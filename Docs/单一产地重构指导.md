# 单一产地重构指导

本文接 [呈现层重构指导.md](呈现层重构指导.md)。那一轮（步 0′~6）已全部落地：工具不再手拼文本，
措辞、排序与「别忘了」归 `Tools/Output/`。**本文管的是它没覆盖的两层——文法闸与参数层。**

体例沿用前文：目标 / 判据 / 步骤表 + 逐步结论栏。契约仍以两处为准：**README 的输出契约章节**
（调用方视角的规格）与**现有测试**（可执行的规格）。

> 状态：**已细化**。§2 的动机在细化过程中拿到了三条实证（词表已漂移、`first 1 preview lines`
> 线上在输出、名词产地有两处是变量），排序据此调整过：新增的 N0 排在最前，因为它已经有一只
> 抓在手里的猎物。步骤表的判据与拆分逐条可执行，结论栏待填。

## 1. 远期目标

不是一批任务，是一条要成立的性质：

> **每一条输出记号只有一个产地，而闸断言的是「没有第二个产地」，不是「文本里没出现违规」。**

三层各有一个权威：

| 层 | 权威 | 现状 |
| --- | --- | --- |
| 呈现层 | `Tools/Output/`（15 个文件 1548 行） | ✅ 前一轮达成 |
| 文法闸 | — | ✗ [GrammarRules.cs](../Sources/RimSearcher.Tests/GrammarRules.cs) 426 行正则 + 5 张手维护的字符串表，**已实测漂移**（见 §2 甲） |
| 参数层 | — | ✗ schema、取参别名、usage 文案、未知键提示四份手写 |

配套的常驻规矩：**新记号加入的顺序是「先在 `Output/` 落一个产地 → 在闸里登记 → 才有第一个调用方」**，
不是反过来。前一轮验证的「先立字节级闸再改代码」是它的一个特例。

## 2. 动机：闸**已经**随产品长大而静默失效

三条，都是这一轮细化时实测出来的，也是排序依据。

### 甲、词表不是「会」漂移，是从落地那天起就漂着的

两个名词槽**都只验形状，从不对词表校验**：

- 折叠行的槽（[GrammarRules.cs:67](../Sources/RimSearcher.Tests/GrammarRules.cs)）只查「非空 且 首词不在 `NotNouns` 里」
  ——`... +7 more nothing (…)` 能过闸；
- `N of M` 的槽只查「下一个字符是字母」——`5 of 12 in scope 'all'` 里 `in` 就是那个「名词」；
- 而单复数那条规则[明写](../Sources/RimSearcher.Tests/GrammarRules.cs)「名词落在词表之外时这条跳过」。

三条合起来：**没登记进 `CountedNouns` 那 28 个词的新名词，覆盖是零。**闸自己的注释早就警告过
这件事（「新加一个计数名词却不登记在这里，那个槽位的单复数就没人守」）——警告在，机制不在。

**而它已经发生了。**28 项里有 4 项在产品侧一处字面量都没有：

| 闸里登记的 | 产品侧的实际情况 |
| --- | --- |
| `changed sources` | 0 处。真名词是 `checked sources`（[SyncSourcesTool.cs:339](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs)），**它不在词表里** |
| `preview lines` | 0 处走构词。表头是手拼的（[ScanOutputRenderer.cs:95](../Sources/RimSearcher.Server/Tools/Output/ScanOutputRenderer.cs)） |
| `name keys` | 只出现在 `more than {cap} name keys`，不是 `N <名词>` 形 |
| `defs` | 只是 `AppConfig` 里的配置键名，不是计数名词 |

`git log -S'"changed sources"' -- Sources/` 只有一个 commit，正是引入 `CountedNouns` 的那次
（7f3b7ce）。**这个词从没对应过任何产品字面量**——写闸的人凭印象写下它，而产品那边一直叫
`checked sources`，于是这一格从第一天起就既守不住任何东西、也没有任何人守。

这条把 M3 从「理论债」升格成「已发生的事故」，故它不再是可选项。

### 乙、真正漏掉那条活缺陷的，是矩阵少了一个维度

`first 1 preview lines` **是线上正在输出的话**。对真实语料实测：

```
Regex matches for 'CompTick' (first 1 preview lines in scope 'vanilla', case-insensitive):
```

要紧的是：**闸的规则二甲本来就抓得住它**（`OnePlus` 匹配 `1 preview lines`，`lines` 以 s 结尾、
不在 `NotNouns` 里 → 判违规），它是纯结构判定，压根不查词表。抓不到的原因不在闸的规则，
在[矩阵](../Sources/RimSearcher.Tests/OutputGrammarGateTests.cs)：15 个分支维度里**没有「计数恰好为 1」**。
两个 `ScanStopped` 格用的都是 `limit = 4`。

而 R30（`... +1 more C# types`）那条历史缺陷正是这个形状，闸的注释也写着「历史缺陷全部落在
N==1 这一侧」——判据在，喂给它的 fixture 不在。

故补维度比补词表更便宜也更前置：它不动产品一行代码就能红，且已经有一只抓在手里的猎物。

### 丙、记号语义被夸大地写进了注释

基线里 24 处 `of`：

| 用法 | 处数 | 例 |
| --- | --- | --- |
| 截断记号 `<数> of <数> <名词>` | 11 | `10 of 21 C# types`、`+4 more of 7 matching lines` |
| 普通英文介词 | 11 | `Subclasses of 'X'`（7 处）、`lines of a N-line file`、`tokens of that length` |
| 区间形 `<数>-<数> of <数>` | 2 | read_code 的 `(lines 2-30 of 30)` |

一半是改不掉的普通介词，故 `of` 这个词永远不可能只有一个含义。闸执行的其实是窄得多的
`\d+ of \d+`（还专门豁免了区间形，理由记在 `NofM` 那条正则上方）。**要改的是注释，不是输出。**

## 3. 约束与判据

沿用前一轮，逐条仍然有效：

1. **输出字节级一致**，除非该步就是为了改输出（那时基线 diff 必须逐条人工核对，并写进 commit 说明）。
2. **文案与结构分两个 commit。**这条让「红」恒等于「结构被改坏了」。
3. **加闸在改动之前。**事后补的基线证明不了「输出一个字没变」。模式：先起 `test:` commit 在
   未改动的代码上生成基线，再起 `refactor:` / `fix:` commit 动代码。
4. 每步一个 commit。本地直接做在 master；远程会话（Claude Code on the web 之类）走各自指定的
   分支，推完再并——判据一条不变，变的只是落点。
5. 构建/测试前先停掉 `rimsearcher-dev` MCP server（它锁着 `Sources/.build`）。
6. **闸与产品只许共用「名单」，不许共用「判断」。**共用判断会让两边同时瞎——写错的东西在闸和
   产品里都合法。这条是 M3 的设计约束。

**非目标**：Core 的索引与查询逻辑；协议层（`RimSearcher.cs` / `ToolResult`）；工具 Description
的内容（只动其中被证伪的陈述，不重写）。

## 4. 中期计划

| # | 步骤 | 一句话判据 | 结论 |
| --- | --- | --- | --- |
| M1 | **`inspect` / `sync_sources` 的字节级覆盖补齐** | 每一形一份基线，在**未改动的代码**上生成、单独一个 `test:` commit | — |
| M2 | **结构类文法规则改成产地断言** | 59 份基线零 diff（纯测试侧改动，输出不许动一个字） | — |
| M3 | **词汇类改成注册表** | 红的判据从「复数写错了」变成「出现了名单外的计数名词」 | — |
| M4 | **参数层：`ScopeArgs` 改名** | 机械替换 60 处引用，59 份基线零 diff | — |

> 基线份数以 **59** 为准（`Snapshots/` 下 .txt 计数）。文档前一版写 58，是上一个 commit
> （82119f7，成员大纲折叠行）加进来之前的数。改动这个数的步骤要在 commit 说明里点出来。

### M1 的拆分：先盘形态，再一形一份

现状 **inspect 4 份 / sync_sources 3 份**，对比 locate 16、search_regex 15、trace 14，而这两个
工具的字面量体量是最大的两个（`InspectTool` 641 行 131 处、`SyncSourcesTool` 864 行 193 处，
口径为长度 ≥4 的字符串字面量）。它是任何触碰这两个工具的前置——不做它，那两个工具就是永久禁区。

待补形态的**候选**清单（从返回点与既有 `*Tests.cs` 的命名反推，落地前先照 §6 的办法逐形核一遍，
不要拿这张表当全集）：

| 工具 | 已有 | 候选待补 |
| --- | --- | --- |
| inspect | type-outline、def、outline-fold、linked-types-fold | XML 分页（`xmlStartLine`）、继承链、`defType` 消歧、def 模式下 `limit` 被忽略那句 Note、`not found` 的两形（scope 内没有但别处有 / 根本不存在）、大纲的 scope 措辞 |
| sync_sources | check、diff-page-fold、diff-member-fold | 单文件 diff（`file=`）、版本回溯（`requested N versions back`）、无归档时的 diff、无变化时的 check、`granularity` 的其余取值 |

每一形一个 `[Fact]`，一份基线，**在未改动的代码上生成**。全部落在一个 `test:` commit 里——
它不改产品一行，故这个 commit 恒绿，是后面所有步骤的地基。

### M2 的拆分：三条规则各自的产地

三条现在各自用正则把文法重新声明了一遍。逐条对应：

| 规则 | 现在的声明 | 该往回验的产地 |
| --- | --- | --- |
| 折叠行形状 | `FoldLine` / `FoldTail` 两条正则 + `IsPerFileFold` | `Fold.Line` / `Fold.Explicit` / `Fold.PerFile`（三者最终都汇到 `OutputText.FoldLine` 与 `Fold.cs:81`） |
| `N of M` | `NofM` 正则（含区间豁免） | `Tally.Cell` 的 `N of M` 分支 + `Fold.PerFile` + `OutputText.FoldLine` 的 `total` 支 |
| `at least` 必带成因 | 四张字符串表（`FloorCauses` / `FloorDecoys` / `FloorPointers`）+ 三处 `Contains` | `ScanReport.FoundCount` / `.LowerBoundReason` / `Tally.Cell` 的 `totalIsLowerBound` 支 |

注意区间豁免（read_code 的 `lines 2-30 of 30`）在改成产地断言之后**自动消失**：它之所以要豁免，
正是因为正则认的是文本而不是产地，而那一形根本不出自上面任何一处。这条是这一步收益的度量——
豁免删得掉，说明真的换成了产地断言；删不掉，说明只是把正则挪了个地方。

### M3 的拆分：注册表不能是「一张字面量清单」

关键发现：**名词的产地是调用点的实参，而其中两处是变量。**

- 走 `OutputText.Quantity` / `NounFor` 的直接调用约 20 处，实参是字面量；
- 走 `Fold.Line` / `Fold.Explicit` / `Fold.PerFile` / `Tally.Cell` 的 11 处调用，名词从实参进来；
- 其中 **[LocateRenderer.cs:46/63](../Sources/RimSearcher.Server/Tools/Output/LocateRenderer.cs) 传的是 `section.Noun`**
  （运行时取 `C# types` / `members` / `XML defs` / `content matches` / `files` 之一），
  **[RoslynHelper.cs:343](../Sources/RimSearcher.Core/Core/RoslynHelper.cs) 传的是 `kindPlural`**
  （运行时取 `methods` / `properties` / `fields`）。

于是注册表的形状不能是「把 28 个字面量搬个家」——那样两个变量槽照样在名单之外。要登记的是
**名词槽本身**：给计数名词一个类型（例如 `readonly record struct CountedNoun`），`Quantity` /
`NounFor` / `Fold.*` / `Tally.Cell` 只收这个类型。这样 `section.Noun` 与 `kindPlural` 的类型
就是它，赋值处自动落进名单，**新名词编译期就进不来**。

**构造入口住 `RimSearcher.Core`（`OutputText` 旁边），不是 `Server` 的 `Output/`。**两个变量槽里的
`RoslynHelper.kindPlural` 就在 Core 里，而项目引用是 `Server → Core` 单向的——入口放进 `Output/` 时
Core 那个槽根本够不到，等于一开始就漏掉一半。这不是妥协：`NounFor` 因为「Core 的大纲也要构词」本就
住在 `OutputText`，[前文](呈现层重构指导.md)步 5 把 `Fold.Explicit` 那一形下沉成 `OutputText.FoldLine`
走的是同一条路，判据也同一条——**不含成因判断才下得去**，而计数名词是纯名单加构词，不读
`ScopeArgs.HardLimit` / `ResultLimit`，下得去。

闸这边照 §3 判据六：只取那份名单，判断仍归自己写。红的判据是「文本里出现了名单外的计数名词」，
不是「复数写错了」。

M3 落地时**顺手清掉甲那四项死表项**，并把 `checked sources` 补进去——但那是改闸不改产品，
59 份基线仍须零 diff。

### M4 的拆分：改名的实际规模

`ScopeArgs` 现在只有 3 个成员碰 scope，被用最多的是 `HardLimit`。实测引用分布：

| 成员 | 产品侧 | 测试侧 |
| --- | --- | --- |
| `HardLimit` | 15 | 16 |
| `GetDisplayLimit` | 5 | 9 |
| `Resolve` | 5 | 1 |
| `ScopeSchemaProperty` | 5 | 0 |
| `LimitSchemaProperty` | 3 | 0 |
| `DefaultDisplayLimit` | 0 | 1 |

合计 60 处、跨 15 个文件。文档前一版写的「`HardLimit` 12 处引用」偏低，实际 31。

`ToolArgs` **不合并**——那是*机制*（怎么从 `JsonElement` 取值），这是*那两个跨工具参数的政策*。
声明式参数规格（`jsonschema-hand-sync-debt`）留在末尾**评估**，不预先承诺：它是理论债，
十三轮盲测没在这儿出过事故。M3 落地之后再评估——那时「一处登记、多处取用」这套做法在本仓
已经有一个跑过的先例，评估才有依据。

## 5. 近期计划

| --- | --- | --- | --- |
| N0 | **矩阵补「计数恰好为 1」维度**，并修掉它抓出来的 `first 1 preview lines` | 加格子即红，红的原文可预知；修完转绿 | — |
| N1 | **`shallowest first` 移进 `Fold.Line` 的「哪一批」槽** | 3 份基线定向变化 + 先补 1 份缺失基线 | — |
| N2 | **`ConditionalReport` 迁入 `Output/`** | 59 份基线零 diff；只改 using 与限定名 | — |
| N3 | **改掉「看到 `of` 就是被截了」这句夸大** | 输出一个字不动，59 份基线零 diff | — |

### N0：补维度，然后修它抓出来的那条

两个 commit，顺序不能反（§3 判据三）：

1. **`test:`** —— 给 `first 1 preview lines` 立一份字节级基线（`search_regex/scan-stopped-single`，
   `limit = 1`），钉住**现状**。这个 commit 恒绿：快照闸不判文法，它只记录「今天是这样」。
2. **`fix:`** —— 往 `AllBranches` 加一维 `SingleCount`（「计数恰好为 1」），七个工具各给一格
   或写明不适用；同 commit 把 [ScanOutputRenderer.cs:95](../Sources/RimSearcher.Server/Tools/Output/ScanOutputRenderer.cs)
   的手拼表头改走 `OutputText.Quantity(…, "preview lines")`，并顺带核一遍
   [ScanReport.cs:55](../Sources/RimSearcher.Server/Tools/Output/ScanReport.cs) 的
   `server cap of {previewCap} preview lines`（同一条修法，只是 previewCap 取 1 的路径当前到不了）。
   第 1 步那份基线在这里出现 diff，逐字核对后更新，写进 commit 说明。

这一改**同时把词表里一个死项变活**：`preview lines` 从此真的经过 `NounFor`，`CountedNouns` 里
那一格开始守东西。这是 M3 的一个提前兑现的小样本。

新维度的每一格都要给 `Expect`（矩阵自己那条 fixture 退化检测要求的），否则语料一改，这一维会
悄悄退回「计数恰好为 4」而闸照绿。

### N1：先补一份缺失的基线，再动槽

`lower relevance,` 现在是 [Fold.cs:80](../Sources/RimSearcher.Server/Tools/Output/Fold.cs) 里写死的
bool 分支；N1 把它变成「哪一批」槽的第一个居民，inheritors 的 `shallowest first` 是第二个。
[InheritorsRenderer.cs:131](../Sources/RimSearcher.Server/Tools/Output/InheritorsRenderer.cs) 那条注释
自己说过它该在哪：「**尾行**只说『被截了』，没说截的是哪一批」——尾行就是折叠行。

两个分支保留：`nothing deeper than depth N is listed`（切片没触到最深层，藏起来的里面有更深的）
与 `shallowest first`（切片已触到最深层，藏的是同深度里的其余）是**两件不同的事实**，
不是一件事的两个精度。

**细化时发现的前置**：`lower relevance` 在 59 份基线里**一处都没有**（`grep -rl` 零命中）——
断层收口那一形只被矩阵的 `locate / ScoreGap` 格与 `OutputReadabilityTests` 的 Contains 断言守着，
没有字节级判据。而 N1 恰恰要改它的产地。故 N1 也是两个 commit：

1. **`test:`** —— 补一份 locate 断层收口的基线（`locate/score-gap-fold`）。此后 60 份。
2. **`refactor:`** —— 动槽。定向变化的是 3 份 inheritors 截断基线
   （`inheritors-truncated`、`inheritors-slice-shallower`、`inheritors-truncated-spanning-sources`），
   新补的那份与其余 56 份必须零 diff。

### N2：搬家的规模

`ConditionalReport` [自己写着](../Sources/RimSearcher.Server/Tools/ConditionalReport.cs)「分工与
`ScopeReport` 完全同型，理由也一样」，而 `ScopeReport` 在 `Output/`、它在 `Tools/`。
前一轮步 0「纯搬家」漏下的一处。

规模：26 处引用、跨 14 个文件（其中 6 个已在 `Output/` 里）。纯搬家，基线零 diff。

**落地实测比这还小：一处调用点都不用改。**除文件本身的 `namespace` 一行外，diff 是空的——
六个引用它的工具类早就为别的 `Output/` 成员写了 `using RimSearcher.Server.Tools.Output;`，
测试侧同理。这本身就是这一步该做的证据：它此前住在 `Tools/` 不是因为有谁依赖那个位置，
纯粹是步 0「纯搬家」漏下的一处。

理由就是 §2 那个发现：现在的闸分不清 `5 of 12 subclasses` 与 `5 of 12 in scope`，

### N5 的待决项：主题行改不改

| 选项 | 写法 | 代价 |
| --- | --- | --- |
| 不改主题行 | `Subclasses of 'ZzBase' (5 of 12 subclasses in scope 'all', …)` | 一行里 subclasses 两遍 |
| 改成 locate 的形状（倾向） | `## 'ZzBase' — 5 of 12 subclasses (in scope 'all', …)` | 口径真正统一，但是这个工具的外观变化 |

**代价实测比原先估的小。**受影响的是**含 `Subclasses of` 表头的 7 份**基线，不是 trace 全部 14 份：
另外 3 份 inheritors 是零命中 / 未知类型形（那条表头压根不存在），4 份 usages 用的是另一个表头
（`Text matches for …`）。两个选项落在同一批 7 份上，故「改主题行更贵」这条理由不成立——
两者的基线代价基本相同，差别只剩外观。

**已定：改成 locate 的形状。**判据是「重构期取统一且准确」——「跨工具口径一致」本来就是这条线的
目标，既然两个选项的基线代价相当（同一批 7 份），差别只剩外观，那么留下一处需要解释的重复就是
纯亏。落地时那 7 份基线逐字核对后更新，写进 commit 说明。

### 口径证据：四个表头，四种说法说同一对数

N5 要消掉的就是这张表的前两行不一致：

```
locate            ## 'ZzThing' — 10 of 21 C# types (1 at 100%), 10 of 20 members
trace inheritors  Subclasses of 'ZzBase' (12 in scope 'all', …). Listed below: 5, shallowest first:
trace usages      Text matches for 'ZzMark' (first 10 preview lines in scope 'all', …):
search_regex      Regex matches for 'ZzNeedle' (3 matching lines in scope 'all', …):
```

| 工具 | 「印了几条」 | 「一共几条」 | 截断记号 |
| --- | --- | --- | --- |
| locate | 第一个数 | 第二个数 | `of` |
| inheritors | **最后**一个数，另起一句 | **第一个**数 | 无 |
| usages | 第一个数，量纲是**预览行**不是命中 | 不给（停扫时确实不可知，有据） | 无 |

locate 与 inheritors 的两个数**顺序正好相反**。从 locate 学到「第一个数是印出来的」的读者，
会把 inheritors 的 12 读成印了 12 条。[Tally.cs:19](../Sources/RimSearcher.Server/Tools/Output/Tally.cs)
写的正是这件事（「两个口径撞在同一个位置上，这才是要害」），但那次**只改了 locate 一边**：
碰撞从「一边缺一个数」降级成「两边顺序相反」，没有消掉。

更硬的一条：`of` 在这台服务器上是有辖域的记号（`Fold.PerFile`、`Fold.Explicit` 的总数形、
`Tally.Cell`、sync_sources 都在用），**inheritors 是唯一一处传达同一个事实却不用它的地方。**

  `SymbolRow` / `FootnoteBlock` 都成型了，
  Header 与 Section 没有——同上，形状是故意不同的。它们该共用的是 Row 与 Footnote，已经共用了。
- **把 `ScopeArgs` 并进 `ToolArgs`**（见 M4）。
- **给 `inspect` / `sync_sources` 做模型。**只服务一个 renderer 的模型不是契约，只是把同一堆
  字符串挪个地方，还多一层间接。它们该接的是文法原语，前一轮步 5 已接完。
