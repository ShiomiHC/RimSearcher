# 单一产地重构指导

本文接 [呈现层重构指导.md](呈现层重构指导.md)。那一轮（步 0′~6）已全部落地：工具不再手拼文本，
措辞、排序与「别忘了」归 `Tools/Output/`。**本文管的是它没覆盖的两层——文法闸与参数层。**

体例沿用前文：目标 / 判据 / 步骤表 + 逐步结论栏。契约仍以两处为准：**README 的输出契约章节**
（调用方视角的规格）与**现有测试**（可执行的规格）。

> 状态：**已细化**。§2 的动机在细化过程中拿到了三条实证（词表已漂移、`first 1 preview lines`
> 线上在输出、名词产地有两处是变量），排序据此调整过：新增的 N0 排在最前，因为它已经有一只
> 抓在手里的猎物。步骤表的判据与拆分逐条可执行，结论栏待填。

## 1. 远期目标

不是一批任务，是一条要成立的性质：

> **每一条输出记号只有一个产地，而闸断言的是「没有第二个产地」，不是「文本里没出现违规」。**

三层各有一个权威：

| 层 | 权威 | 现状 |
| --- | --- | --- |
| 呈现层 | `Tools/Output/` + `Core/`（16 个文件 1738 行，另加 `CountedNoun` / `OutputText` 两处下沉到 Core） | ✅ 前一轮达成 |
| 文法闸 | [GrammarRules.cs](../Sources/RimSearcher.Tests/GrammarRules.cs)（610 行）问产地，产地在 `Output/` | 🟡 九条规则里八条到位。五张手维护的字符串表全删（M2/M3/N4），描述文法的正则只剩规则八那两句内插——**它是活规则**（8 份基线上真的在跑）**且失效形态仍是「继续绿」**。见 M5 |
| 参数层 | 取参别名 → `ScopeAndLimitArgs.ScopeKeys` / `LimitKeys`；未知键提示 → 产品自己的 `UnknownKeyNotice` | 🟡 四份手写收了两份（`8ca8ed6`，两侧各立一道闸）。剩 **schema** 与 **usage 文案**两份，见 [参数层单一产地重构指导.md](参数层单一产地重构指导.md) |

原表把文法闸与参数层一律记作 ✗。M 系做完后两层都成了「部分到位」，而 ✗ / ✅ 两档表达不了这件事——
真正要紧的从来不是打几个勾，是**剩下的那一块的失效形态是什么**。故现状栏一律写到「哪一条没收口、
它坏起来是红还是绿」为止：绿着坏的（规则八、schema）比红着坏的急，因为没人会发现。

配套的常驻规矩：**新记号加入的顺序是「先在 `Output/` 落一个产地 → 在闸里登记 → 才有第一个调用方」**，
不是反过来。前一轮验证的「先立字节级闸再改代码」是它的一个特例。

## 2. 动机：闸**已经**随产品长大而静默失效

三条，都是这一轮细化时实测出来的，也是排序依据。

### 甲、词表不是「会」漂移，是从落地那天起就漂着的

两个名词槽**都只验形状，从不对词表校验**：

- 折叠行的槽（[GrammarRules.cs:67](../Sources/RimSearcher.Tests/GrammarRules.cs)）只查「非空 且 首词不在 `NotNouns` 里」
  ——`... +7 more nothing (…)` 能过闸；
- `N of M` 的槽只查「下一个字符是字母」——`5 of 12 in scope 'all'` 里 `in` 就是那个「名词」；
- 而单复数那条规则[明写](../Sources/RimSearcher.Tests/GrammarRules.cs)「名词落在词表之外时这条跳过」。

三条合起来：**没登记进 `CountedNouns` 那 28 个词的新名词，覆盖是零。**闸自己的注释早就警告过
这件事（「新加一个计数名词却不登记在这里，那个槽位的单复数就没人守」）——警告在，机制不在。

**而它已经发生了。**28 项里有 4 项在产品侧一处字面量都没有：

| 闸里登记的 | 产品侧的实际情况 |
| --- | --- |
| `changed sources` | 0 处。真名词是 `checked sources`（[SyncSourcesTool.cs:339](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs)），**它不在词表里** |
| `preview lines` | 0 处走构词。表头是手拼的（[ScanOutputRenderer.cs:95](../Sources/RimSearcher.Server/Tools/Output/ScanOutputRenderer.cs)） |
| `name keys` | 只出现在 `more than {cap} name keys`，不是 `N <名词>` 形 |
| `defs` | 只是 `AppConfig` 里的配置键名，不是计数名词 |

`git log -S'"changed sources"' -- Sources/` 只有一个 commit，正是引入 `CountedNouns` 的那次
（7f3b7ce）。**这个词从没对应过任何产品字面量**——写闸的人凭印象写下它，而产品那边一直叫
`checked sources`，于是这一格从第一天起就既守不住任何东西、也没有任何人守。

这条把 M3 从「理论债」升格成「已发生的事故」，故它不再是可选项。

### 乙、真正漏掉那条活缺陷的，是矩阵少了一个维度

`first 1 preview lines` **是线上正在输出的话**。对真实语料实测：

```
Regex matches for 'CompTick' (first 1 preview lines in scope 'vanilla', case-insensitive):
```

要紧的是：**闸的规则二甲本来就抓得住它**（`OnePlus` 匹配 `1 preview lines`，`lines` 以 s 结尾、
不在 `NotNouns` 里 → 判违规），它是纯结构判定，压根不查词表。抓不到的原因不在闸的规则，
在[矩阵](../Sources/RimSearcher.Tests/OutputGrammarGateTests.cs)：15 个分支维度里**没有「计数恰好为 1」**。
两个 `ScanStopped` 格用的都是 `limit = 4`。

而 R30（`... +1 more C# types`）那条历史缺陷正是这个形状，闸的注释也写着「历史缺陷全部落在
N==1 这一侧」——判据在，喂给它的 fixture 不在。

故补维度比补词表更便宜也更前置：它不动产品一行代码就能红，且已经有一只抓在手里的猎物。

### 丙、记号语义被夸大地写进了注释

基线里 24 处 `of`：

| 用法 | 处数 | 例 |
| --- | --- | --- |
| 截断记号 `<数> of <数> <名词>` | 11 | `10 of 21 C# types`、`+4 more of 7 matching lines` |
| 普通英文介词 | 11 | `Subclasses of 'X'`（7 处）、`lines of a N-line file`、`tokens of that length` |
| 区间形 `<数>-<数> of <数>` | 2 | read_code 的 `(lines 2-30 of 30)` |

一半是改不掉的普通介词，故 `of` 这个词永远不可能只有一个含义。闸执行的其实是窄得多的
`\d+ of \d+`（还专门豁免了区间形，理由记在 `NofM` 那条正则上方）。**要改的是注释，不是输出。**

> **N5 之后这张表的处数变了**（结论没变）：`Subclasses of 'X'` 那 7 处普通介词被表头改造整批
> 换掉，现在是 15 处截断记号 / 4 处普通介词 / 2 处区间形。三类**并存**这件事才是辖域必须写窄
> 的理由，故落地时把注释里的具体计数一并去掉了——那种数字会随任何一次输出改动而漂，
> 是下一轮「注释语义偏离」的现成材料。

## 3. 约束与判据

沿用前一轮，逐条仍然有效：

1. **输出字节级一致**，除非该步就是为了改输出（那时基线 diff 必须逐条人工核对，并写进 commit 说明）。
2. **文案与结构分两个 commit。**这条让「红」恒等于「结构被改坏了」。
3. **加闸在改动之前。**事后补的基线证明不了「输出一个字没变」。模式：先起 `test:` commit 在
   未改动的代码上生成基线，再起 `refactor:` / `fix:` commit 动代码。
4. 每步一个 commit。本地直接做在 master；远程会话（Claude Code on the web 之类）走各自指定的
   分支，推完再并——判据一条不变，变的只是落点。
5. 构建/测试前先停掉 `rimsearcher-dev` MCP server（它锁着 `Sources/.build`）。
6. **闸与产品只许共用「名单」，不许共用「判断」。**共用判断会让两边同时瞎——写错的东西在闸和
   产品里都合法。这条是 M3 的设计约束。

**非目标**：Core 的索引与查询逻辑；协议层（`RimSearcher.cs` / `ToolResult`）；工具 Description
的内容（只动其中被证伪的陈述，不重写）。

1. **规则九乙一并改了。**它的 `server cap \d+ reached` 正则 + `pass limit:'all'` 字面量与本步三条
   同一形状，两句提示语改成从 `Fold.Line` 渲染回来（产地是它的局部变量，够不着，故连着折叠行整句

   件事的两面。规则编号与两个违规名都保留（别处有六处交叉引用），报哪一个只影响措辞。
3. **规则四的诱饵表整张删掉**，甲从「同屏有诱饵时才要引用」升格成「一律要引用」。「读者可能拿来
   解释这个下界的别的上限句」是个开放集合，枚举得出的那四条挡不住第五句。现存三份带 `at least`

**收益的独立验证**（做完之后临时做的一次变异，已回滚）：把 `OutputText.FoldLine` 的排版整个换掉

### M3 的拆分：注册表不能是「一张字面量清单」

关键发现：**名词的产地是调用点的实参，而其中两处是变量。**

- 走 `OutputText.Quantity` / `NounFor` 的直接调用约 20 处，实参是字面量；
- 走 `Fold.Line` / `Fold.Explicit` / `Fold.PerFile` / `Tally.Cell` 的 11 处调用，名词从实参进来；
- 其中 **[LocateRenderer.cs:46/63](../Sources/RimSearcher.Server/Tools/Output/LocateRenderer.cs) 传的是 `section.Noun`**
  （运行时取 `C# types` / `members` / `XML defs` / `content matches` / `files` 之一），
  **[RoslynHelper.cs:343](../Sources/RimSearcher.Core/Core/RoslynHelper.cs) 传的是 `kindPlural`**
  （运行时取 `methods` / `properties` / `fields`）。

于是注册表的形状不能是「把 28 个字面量搬个家」——那样两个变量槽照样在名单之外。要登记的是
**名词槽本身**：给计数名词一个类型（例如 `readonly record struct CountedNoun`），`Quantity` /
`NounFor` / `Fold.*` / `Tally.Cell` 只收这个类型。这样 `section.Noun` 与 `kindPlural` 的类型
就是它，赋值处自动落进名单，**新名词编译期就进不来**。

**构造入口住 `RimSearcher.Core`（`OutputText` 旁边），不是 `Server` 的 `Output/`。**两个变量槽里的
`RoslynHelper.kindPlural` 就在 Core 里，而项目引用是 `Server → Core` 单向的——入口放进 `Output/` 时
Core 那个槽根本够不到，等于一开始就漏掉一半。这不是妥协：`NounFor` 因为「Core 的大纲也要构词」本就
住在 `OutputText`，[前文](呈现层重构指导.md)步 5 把 `Fold.Explicit` 那一形下沉成 `OutputText.FoldLine`
走的是同一条路，判据也同一条——**不含成因判断才下得去**，而计数名词是纯名单加构词，不读
`ScopeAndLimitArgs.HardLimit` / `ResultLimit`（M4 之前叫 `ScopeArgs`），下得去。

闸这边照 §3 判据六：只取那份名单，判断仍归自己写。红的判据是「文本里出现了名单外的计数名词」，
不是「复数写错了」。

M3 落地时**顺手清掉甲那四项死表项**，并把 `checked sources` 补进去——但那是改闸不改产品，
61 份基线仍须零 diff。

#### M3 落账（`d77db5a`）

按上面的形状做了：`CountedNoun` 是个 `sealed class`（不是预案里写的 `readonly record struct`——
名词要按**同一性**比较而不是按值，`Dictionary<CountedNoun, int>` 那个槽在 `ScopeReport` 里，
引用相等正好是想要的语义），私有构造 + 静态 `Register`，26 个成员，住

**与预案的两处出入，都是收益方向：**

### M5 的拆分：最后一条手抄文法的规则

规则八（自洽）判的是「表头说 `N of M <名词>`、同一份返回里又有 `... +K more <同名词>` 时，
N + K 必须等于 M」。**判据本身是对的且值钱**（R47 那次表头与折叠行各说各的，两个数没一处对得上），
问题只在它怎么找到那两个数：两句手抄的内插正则。

两句各对应一个已经存在的产地，故收口是直译：

| 手抄的 | 它抄的是谁 | 换成 |
| --- | --- | --- |
| `\b(?<n>\d+) of (?:the )?(?:at least )?(?<m>\d+) <名词>\b` | `Tally.Cell` 的 `N of M` 支（`(?:at least )?` 抄的是 `ScanReport.FloorMark`、`(?:the )?` 抄的是 `Fold` 某处的介词） | 手法乙：对行内整数 × `NounsMentionedIn` 试 `Tally.Cell(n, m, noun)` 与 `Tally.Cell(n, m, noun, true)`，命中即取那对 `(n, m)` |
| `\.\.\. \+(?<k>\d+) more <名词>\b` | `OutputText.FoldLine` 的框架 | 手法甲：`CommonPrefix`/`CommonSuffix` 求出框架，切出 `K` 槽 |

三处要当心，都是「改完仍绿但判据没了」的入口：

1. **先量后改。**当前命中是 8 份基线 / 9 对配对（`locate` 5 份 × `files` / `members` / `C# types`，
   `trace` 3 份 × `subclasses`）。M5 的第一个动作是把这个计数落成一个**可执行的断言**——
   否则收口后闸照绿，而绿有两个原因（都对上了 / 一对都没找着），从外面分不出来。
   这正是 M2 变异实验漏掉的那件事，见上。
2. **`(?:the )?` 与 `(?:at least )?` 这两个可选段是线索。**它们说明当年抄的时候，产地那边这两截
   本来就不止一形。换成产地断言之后它们不该以「可选段」的形式活下来——`Tally.Cell` 的
   `totalIsLowerBound` 两支各渲染一次就够，渲染不出来的形本来就不该放行。
3. **N + K = M 这条加法留在闸里，不许下沉。**它是**判断**不是名单（§3 判据六）。产地只负责回答
   「这两个数出自哪里」，两个数该不该相等由闸自己说——真让产品去保证的话，这条规则就变成了
   「产品自己检查自己」，R47 那种缺陷正是产品两处各算各的算出来的。

判据：73 份基线零 diff（纯测试侧；两个产地都已存在，不像 M2 那样要先补产品），929 全绿，
且第 1 条那个命中计数一次不少。

- **还有 README 的三处**（折叠行那节、locate 表头那节、trace inheritors 那节）。这三处是
  漏不得的：上面五处代码注释里有三处**明写「README 把 of 定成截断记号」**——只收窄注释而留着
  README，注释就比它引的契约更窄，同一条读法又变成两个口径。而 §1 定的两个权威之一正是
  README，假陈述留在权威里，改注释就只是把问题挪了个地方

改成闸实际执行的那条窄陈述：**`<数> of <数>` 这一个计数惯用法里，`of` 表示没给全**。
输出一个字不动，60 份基线零 diff。

### N4：最小改法与它必然抓到的东西

两个槽的名词都对 `CountedNouns` 查一次，查不到就红——折叠行那个槽在
[GrammarRules.cs:205](../Sources/RimSearcher.Tests/GrammarRules.cs)，`N of M` 那个在
[GrammarRules.cs:317](../Sources/RimSearcher.Tests/GrammarRules.cs)。

判据：修完之后 61 份基线仍零 diff（纯测试侧改动）。**如果红了，说明产品里有名词没登记——
那正是它该抓的，不是回退的理由。**

而它**一定会红**：§2 甲已经证到 `checked sources` 是产品里的计数名词却不在词表里。故 N4 落地时
必然要往 `CountedNouns` 加词、删死项——那一步本身就是 M3 的手工版，做完顺势评估 M3 的收益。

#### 落地实况：两个槽补完是绿的，红在别处

上面这个预测**说对了结论、说错了机制**，值得记下来。

两个槽的词表查询补完（含单数式：折叠行在 N==1 时印的正是 `... +1 more C# type`），112 格矩阵
全绿。原因是那三个漂掉的词一个都不落在这两个槽里——`checked sources` 走的是
`OutputText.Quantity`，出现在 sync_sources 的一句结论里，既不是折叠行也不是 `N of M`。

**更根本的是：文本闸看不见这件事。**它吃的是输出，而「这个名词有没有被登记」在输出文本里
根本没有对应物——`3 checked sources are up to date` 无论登记与否都长得一模一样。这不是槽位
补得不够细，是判据的量纲不对。

故 N4 多加了一个 [CountedNounRegistryTests](../Sources/RimSearcher.Tests/CountedNounRegistryTests.cs)，
改吃**产品源码**，双向钉同步：正向（`NounFor` / `Quantity` 第二个实参上的字面量必须在表里）、
反向（表里的词必须在产品源码里出现过）。它一跑就红，抓到的正是 §2 甲手工核对出来的那三行：

```
EveryCountedNounLiteralInTheProduct_IsRegistered
  SyncSourcesTool.cs：'checked sources' 走了构词却不在 CountedNouns 里
EveryRegisteredCountedNoun_IsSpokenByTheProduct
  changed sources
  name keys
```

第四项 `defs` 抓不到：产品里确有 `"defs"` 字面量，那是 `AppConfig` 的配置**键名**。纯文本判定
分不出「同一个词在两种角色上」，故它是手工删的。**这个盲区就是 M3 的收益所在**——给计数名词
一个类型之后，配置键名与计数名词在类型上就是两种东西，不必再靠人眼分辨。

（M3 已落地兑现这一条，见 §4「M3 落账」：扫描口径从字符串 `"defs"` 换成成员引用
`CountedNoun.Defs`，同形碰撞消失。）

顺带的收益是 N5 的前置真的到位了：`5 of 12 subclasses` 与 `5 of 12 in scope` 现在分得开
（反面用例见 `GrammarRulesTests.CountOfTotal_FollowedByAPreposition_IsCaught`）。

#### 附带修掉的一处：闸自称有反例，反例不存在

做 N4 时发现 `GrammarRules` 里有一处注释写着「反面用例见 `GrammarRulesTests`」，而这个类型
在仓库里一直不存在。它不只是个死引用：`OutputGrammarGateTests` 喂的是真输出，只证得了「现在
没有违规」，一条判据是不是**还能红**它答不出来——而闸最坏的失效形态恰恰是「判据坏了但继续
绿」。故补了 25 例正反用例（`7dbf235`），每条判据至少一正一反。这也是新加的名词槽判据自己的
「它真的会红」证明。

### N5：前置已经说清

理由就是 §2 那个发现：现在的闸分不清 `5 of 12 subclasses` 与 `5 of 12 in scope`，
**写法对不对无法被验证**；N4 修好之后这件事才有判据。判据见下面的待决项。

### N5 的待决项：主题行改不改

| 选项 | 写法 | 代价 |
| --- | --- | --- |
| 不改主题行 | `Subclasses of 'ZzBase' (5 of 12 subclasses in scope 'all', …)` | 一行里 subclasses 两遍 |
| 改成 locate 的形状（倾向） | `## 'ZzBase' — 5 of 12 subclasses (in scope 'all', …)` | 口径真正统一，但是这个工具的外观变化 |

**代价实测比原先估的小。**受影响的是**含 `Subclasses of` 表头的 7 份**基线，不是 trace 全部 14 份：
另外 3 份 inheritors 是零命中 / 未知类型形（那条表头压根不存在），4 份 usages 用的是另一个表头
（`Text matches for …`）。两个选项落在同一批 7 份上，故「改主题行更贵」这条理由不成立——
两者的基线代价基本相同，差别只剩外观。

**已定：改成 locate 的形状。**判据是「重构期取统一且准确」——「跨工具口径一致」本来就是这条线的
目标，既然两个选项的基线代价相当（同一批 7 份），差别只剩外观，那么留下一处需要解释的重复就是
纯亏。落地时那 7 份基线逐字核对后更新，写进 commit 说明。

**已做（`0656982`）。**7 份基线，一份不多一份不少，与预估逐字相符。三处额外收益是预估里没有的：

1. `Listed()` 整个删掉——它那个「没被截就不印」的判据逐字等于 `Tally.Cell` 的 `total > shown`，
   属于同一件事的第二处实现，而不只是同一个写法的第二种排版。
2. **规则八（表头 `N of M` 与折叠行 `+K` 自洽）在这个工具上从落空变成生效。**它按名词配对，
   而此前 inheritors 的表头压根没有 `N of M subclasses`，故整条判据在这一列上一次都没跑过。
3. `inheritors-out-of-scope` 的 `1 in scope 'vanilla'` 此前没有名词，现在走构词印出单数式。

代价里有一项预估没算到：`Subclasses of 'X'` 是语料里最多的一种**普通介词** `of`，它一被换掉，
§2 丙那张表以及引用它的三处注释（README、`GrammarRules` 规则三、`Tally`）就同时失准。已在
同一个 commit 内改掉——**这正是「注释语义偏离」必须排在 N 系之后的实证**：先改代码再排查，
排查表才不会被自己造出来的偏离灌满。

### 口径证据：四个表头，四种说法说同一对数

N5 要消掉的就是这张表的前两行不一致：

```
locate            ## 'ZzThing' — 10 of 21 C# types (1 at 100%), 10 of 20 members
trace inheritors  Subclasses of 'ZzBase' (12 in scope 'all', …). Listed below: 5, shallowest first:
trace usages      Text matches for 'ZzMark' (first 10 preview lines in scope 'all', …):
search_regex      Regex matches for 'ZzNeedle' (3 matching lines in scope 'all', …):
```

| 工具 | 「印了几条」 | 「一共几条」 | 截断记号 |
| --- | --- | --- | --- |
| locate | 第一个数 | 第二个数 | `of` |
| inheritors | **最后**一个数，另起一句 | **第一个**数 | 无 |
| usages | 第一个数，量纲是**预览行**不是命中 | 不给（停扫时确实不可知，有据） | 无 |

locate 与 inheritors 的两个数**顺序正好相反**。从 locate 学到「第一个数是印出来的」的读者，
会把 inheritors 的 12 读成印了 12 条。[Tally.cs:19](../Sources/RimSearcher.Server/Tools/Output/Tally.cs)
写的正是这件事（「两个口径撞在同一个位置上，这才是要害」），但那次**只改了 locate 一边**：
碰撞从「一边缺一个数」降级成「两边顺序相反」，没有消掉。

更硬的一条：`of` 在这台服务器上是有辖域的记号（`Fold.PerFile`、`Fold.Explicit` 的总数形、
`Tally.Cell`、sync_sources 都在用），**inheritors 是唯一一处传达同一个事实却不用它的地方。**

N5 之后这张表的第二行成了：

```
trace inheritors  ## 'ZzBase' — 5 of 12 subclasses (in scope 'all', …):
```

四个表头里 usages 与 search_regex 仍是另一形，但那两个**不给总数是有据的**（扫描停了就确实
不可知），不属于同一个问题。

- **给 `inspect` / `sync_sources` 做模型。**只服务一个 renderer 的模型不是契约，只是把同一堆
