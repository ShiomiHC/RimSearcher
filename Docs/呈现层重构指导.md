# 呈现层重构指导

本文是输出呈现层（renderer）重构的指导文档。`输出审计改动记录.md` 与 `输出审计-历史轮次.md` 是历史记录——它们解释每一句输出**为什么**长成现在这样，重构期间只作考证用，不作指导用。重构的契约以两处为准：**README 的输出契约章节**（调用方视角的规格）与**现有测试**（可执行的规格）。

---

## 1. 动机

十三轮盲测修的缺陷几乎全部落在同一层：每个工具各自手拼最终文本，全服文法（截断行、来源标签、下界记号、脚注……）靠「照着别处写」维持一致。证据：

- 文法字符串散在 Tools/ 下 9 个文件里（49 处），StringBuilder 手拼 146 处；
- [ListDirectoryTool.cs:236](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs) 的注释写着「文法与全服统一的截断脚注一致……见 Fold.Line」，下一行**手拼了一条模仿它的字符串**——契约靠模仿与测试事后拦截，不是按构造成立（步 4 收）；
- ~~[ScopeArgs.cs](../Sources/RimSearcher.Server/Tools/ScopeArgs.cs) 596 行里约 430 行与 scope 参数无关，是呈现逻辑没有家、寄居在大家都 using 的地方~~ ✅ 步 0 已解：ScopeArgs 剩 157 行纯参数语义，呈现成员迁入 [Tools/Output/](../Sources/RimSearcher.Server/Tools/Output)（495 行 / 6 个文件）；
- 各工具的脚注**排序**（见 §4 原语表的 Footnote 行）只存在于各 ExecuteAsync 的代码顺序里，没有任何一处把它写成规则。

## 2. 目标形态

```
工具 ExecuteAsync
  ├─ 解析参数（ToolArgs / ScopeArgs 参数部分，不动）
  ├─ 查询（Core，不动）
  ├─ 组装 ToolOutput 模型     ← 工具的新职责边界：说「有什么」，不说「怎么印」
  └─ OutputRenderer.Render(model) → string → ToolResult（协议层无感知）
```

- 模型与 renderer 放 `Sources/RimSearcher.Server/Tools/Output/`。呈现契约是 MCP 面向调用方的话术，不进 Core；Core 的 `ScopedResult` 等保持是数据。
- 全服文法（`... +N more <名词> (<下一步>)`、单复数一致、`<数> of <数>` = 没给全、`at least` 必带成因引用、结尾无空行……）只在 renderer 体内存在一份。工具忘了某条契约应当表现为**模型装不进去 / 测试全红**，而不是某个分支静默漏印。
- [GrammarRules.cs](../Sources/RimSearcher.Tests/GrammarRules.cs)（426 行）从事后检查器变成 renderer 的规格书，内容不改。

## 3. 约束与判据

1. **字节级一致**：迁移期间输出一个字不变。判据分两道：
   - **测试断言零改动全绿**——断言文本一个字不动。类名与 using 的机械替换不算改动（步 0 会把 `ScopeArgs.FoldLine` 这类限定名换掉，测试里有 10 处代码引用跟着换；断言的字符串常量不许动）。
   - **黄金快照闸逐字绿**——现有 828 个断言全是 `Contains` / `DoesNotContain`，没有一处比整份输出，故「测试全绿」判不出「输出一个字没变」。这条约束要成立必须自带判据，见 §5 步 0′。
2. **文案问题只记录、不顺手修**：迁移中发现的措辞缺陷记入本文 §7，全部迁移完成后另起 commit 处理（届时测试与快照基线跟着改）。这样「红了」在整个迁移期恒等于「结构改坏了」。
3. 每步一个 commit，master 直接做（本仓不开 feature 分支）。
4. 构建/测试前先停掉 rimsearcher-dev MCP server（它锁着 `Sources/.build` 输出；进程会自动重连跑新二进制）。

**非目标**（本轮不碰）：

- 参数层（ToolArgs 内聚良好，不拆不改）；
- 协议层（RimSearcher.cs / ToolResult）；
- Core 索引与查询逻辑；
- JsonSchema 与取参别名的手动同步问题（声明式参数规格）——理论债，renderer 完成后再评估；
- 工具 Description / JsonSchema 文案。

## 4. 模型原语（草案，试点期修订）

原语不是凭空设计，全部从现有雏形与 README 契约反推。试点若发现装不下的形态，改原语、更新本表。
「现状雏形」一列指的是步 0 之后的位置（`Sources/RimSearcher.Server/Tools/Output/`）。

| 原语 | 承载 | 现状雏形 |
| --- | --- | --- |
| **Header** | 名词、总数（确定值 \| 下界+成因引用 \| 截断时的 `first N preview lines` 换形）、显示数、量纲（matching lines / preview lines）、`(K at 100%)`、casing/filter 等参数回显、来源构成 | `ScanReport.FoundCount` + `.LowerBoundReason` + 各工具手拼的 headline |
| **Tally** | Header 的多段形：主题 + **逐段计数列表** + scope 标注。locate 的头一行是 `## 'query' — <各段计数> _(scope: X)_`，每格是「显示数 [of 总数] 名词 [(K at 100%)]」，不是单个 Header 装得下的形状 | `LocateTool.Count` + `tally` 列表 |
| **Section** | 名词、总数、截断态（limit / 断层收口 / 无）、来源构成（截断时印构成，各源之和恒等于总数）、行列表 | `SourceLabeling` + `Fold.Line` |
| **Row** | 主体、分数 `(N%)`、文件名（可推导则省；重名补目录）、来源标签（仅混源时）、conditional 键 | `SourceLabeling.Label` / `FileNames.Disambiguate` / `ConditionalReport.Tag` |
| **Fold** | 藏了几条、总数已知否（`of M`）、成因（limit / 配额 / 每文件上限）、下一步动作（capAction 因工具而异）。**第四形已加**（步 4）：下一步与 limit 三分支无关、由工具显式给出（`pass offset=N` / `pass startLine=N`），见 `Fold.Explicit` | `Fold.Line` / `.Explicit` / `.PerFile` / `.PerFilePreviewCap` / `ScanReport.ScanStopped`；inspect / sync_sources 的三条仍是手拼（步 5） |
| **Footnote** | 越界报告（合计+构成规则）、not-scanned-in-full（点名前 3）、preview-cap（整份一次）、conditional 成因、`ScopeNotices.HardScopeFilter`、scopeNotice、**工具自备整句**（locate 的 missingFile / floor / shortToken / prefixNotice、`ScopeNotices.RetryWider`）—— **及排序**（现状 search_regex 的序：scan-stopped/文件折叠 → preview-cap → not-scanned-in-full → conditional → hard-scope → scopeNotice） | `ScopeReport` / `ScanReport.NotScannedInFull` / `ScopeNotices.*` + 各工具尾部拼接顺序 |

`unknown-key`、启动期健康提示、时效提示**不在** renderer 的管辖内：它们由 [RimSearcher.cs:453](../Sources/RimSearcher.Server/RimSearcher.cs) 拼在 `ToolResult.Content` 之后，属 §3 明列为非目标的协议层。renderer 能保证的排序止于 scopeNotice。

另一条不必操心的事：换行。[ToolResult.cs](../Sources/RimSearcher.Server/Tools/ToolResult.cs) 在构造时已统一 `NormalizeNewlines` + `TrimEnd`，故 trace 的 `AppendLine`（Windows 上是 CRLF）与 search_regex 的 `"\n"` 之间的历史差异被那一层吃掉。renderer 一律吐 `\n`，不必复刻各工具的拼法。

已知的跨原语耦合（renderer 必须整体持有模型才能保证的联动，散装 helper 保证不了）：

- 有文件没扫全 ⇒ Header 总数改口 `at least` **且**就地挂成因引用 **且**尾注点名文件——三处联动；
- 扫描停在配额 ⇒ Header 换 `first N preview lines` 形 **且**最后一个文件的折叠不计入 preview-cap 脚注的触发条件；
- Section 被截断 **且**总数跨源 ⇒ 段头印构成；未截断不印。

## 6. 试点（search_regex）需要覆盖的形态清单

从 [SearchRegexTool.cs](../Sources/RimSearcher.Server/Tools/SearchRegexTool.cs) 现状整理，迁移后逐条核对：

- 零命中形（fileFilter 回显 + 候选文件数 + casing + RetryWiderNotice + scopeNotice）；
- 正常形表头（FoundCount / at least + LowerBoundReason / `first N preview lines` 三态）；
- 文件块（排序键=印出来的名字、重名消歧、条件标记在来源标签之前、每文件折叠 `+N more of M`）；
- 文件数超限的两形（truncated 时 extra note「seen so far 不是总数」/ 未截断时 `+N more of M matching files (50 listed; …)`）;
- preview-cap 脚注的触发条件（只算真撞每文件上限的折叠，配额耗尽的最后一个文件不算）；
- not-scanned-in-full 三种成因（超时/读不开/行闸）各自的单复数整句两写 + 点名；
- 来源标签三态（钉死不印 / 同源表头一次 / 混源逐行）+ 截断时 fileScopeTotals 只在扫描没停时给；
- 尾注顺序（§4 Footnote 行）。
