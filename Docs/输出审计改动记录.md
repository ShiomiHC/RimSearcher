# RimSearcher 全量输出审计 · 改动记录

> 本文档是本轮「全量输出测试」的**唯一改动台账**。分支 `claude/rimsearcher-full-output-test-j52pb2`。
> 每条缺陷记：**症状 → 为什么这是缺陷（对调用方的后果）→ 改法 → 回归用例**。
> 判据：**LLM 调用方可用性优先**。一条输出只要会让调用方得出与事实相反的结论，就算缺陷——哪怕代码逻辑本身「没写错」。

---

| 维度 | 裁定 |

## 二、测试装置

### 2.1 MCP 探针

`rsprobe.py`（scratchpad，不入库）：以 stdio 直连 `RimSearcher.Server.dll`，走完整 MCP 握手，
按 JSON-RPC `id` 把 `notifications/logging/message` 与真正的响应分离，逐调用落 `.jsonl` /
`.md` / `.serverlog` 三份。支持 `--config <绝对路径>` 换配置，因此同一批调用可在不同语料上重放。

调用矩阵 **207 条**，覆盖 7 个工具 + 协议层。按「每个参数维度取 有效 / 边界 / 非法 三态」组织，
不做笛卡尔积。

### 2.2 合成 fixture

真实语料填不上的两块，用合成件补：

- **`fixture/src/v1` → `FixtureMod.dll`**（netstandard2.0 真实编译产物，含 enum / delegate /
  interface / 抽象基类 / 派生类 / 属性 override）。v2 增删成员（加 `Overloaded`、`Refill`、
  `FixtureBrandNewType`，删 `Capacity` override）。
  **意义**：`sync_sources` 的「反编译 → 同步 → 改动 → 再同步 → 代际 diff」闭环此前**根本无法测**
  ——没有一个会变的真实 DLL。
- **`fixture/ModLayout`**：`loadFolders.xml` 里放**互斥**条件目录、同一相对路径的 **3 份**
  `Shadowed.xml`（触发文件级 shadowing）、一个 1.5 死目录。
  **意义**：mod 布局展开的取舍分支此前只在真实 mod 上偶发命中，不可控。

## 三、已确认并已修复的缺陷

### F1 · 配置加载失败后，服务照常启动并把「索引是空的」伪装成「这个符号不存在」

**怎么发现的**：我自己踩了。给探针传了**相对路径**的 `--config config-fixture.toml`，服务端按
自己的 exe 目录去解析，日志里写了 `Failed to load configuration | reason=file not found`,
然后——**照常启动**，零个源，并对每一条查询回一句体面的：

```
No results for 'FixtureComp' in scope 'all'.
```

**为什么是缺陷**：那行诊断只到了 **stderr**。启动阶段 `ServerLogger.OnLogAsync` 还没接上 MCP 通道，
而调用方是**只读工具返回文本**的 LLM。于是「服务器没有索引」被读成「代码里没有这个符号」——
这是**方向相反**的结论，且调用方没有任何线索能察觉。同一类症状还包括：配置加载成功但没配源、
配了源但源目录里一个可索引文件都没有。

**改法**：新增 `Sources/RimSearcher.Server/StartupHealth.cs`，两级提示：

- **阻塞级**（`BlockingReason`）：**每一次**工具返回都追加。因为这个会话里的**每一条**「没找到」
  都同样不可信，只说一次等于没说。文案：
  `**Warning: this server has no usable index, so the result above is not evidence of absence.**`
- **忠告级**（`Advisories`）：**每会话一次**（`Interlocked.Exchange` 保证），索引可用、重复即噪音。

`Program.cs` 在索引建完后判定三种阻塞成因并 `StartupHealth.Record(...)`；
`RimSearcher.cs` 在每次响应拼接时 `_startupNotice.Consume()`。

该提示**不受 `SuppressStalenessNotice` 影响**：那面旗关的是「源变了」这类时效提示，
而「索引根本是空的」与时效无关，任何工具都得照说。

配套：`SourceIndexer` / `DefIndexer` 各暴露 `IndexedFileCount`，用来判定「零文件」。

**回归**：`StartupHealthTests.cs`（6 条）——健康则静默 / 阻塞级每次都说 / 忠告级只说一次 /
忠告级不跨会话共享 / 阻塞级压过忠告级 / 空白理由视同健康。

### F2 · mod 布局取舍对调用方完全不可见

**症状**：`loadFolders.xml` 的条件目录选择、同名文件的**文件级 shadowing**（RimWorld 自己的
覆盖规则）都会让一部分文件**不进索引**。这些是工具**替调用方做的决定**，此前只写 stderr 日志。

**为什么是缺陷**：「搜不到某个 def」最可能的解释就是它所在的那份文件被 shadow 掉了。调用方看不到
这件事，就只能得出「这个 def 不存在」。

**改法**：并入 F1 的忠告级通道。`Program.cs` 把 `resolvedSources.Notes` 与
`resolvedSources.Shadowed.Count` 汇成 advisories，随本会话第一条工具返回捎出：
`**Note: the indexed source layout involved choices you cannot see from the results.**`

**回归**：同 `StartupHealthTests.cs`。

**注**：fixture 里那组「互斥条件目录」经 `search_regex` / `trace` 复核**只命中 1 处**，
即 shadowing 按 README 语义正确生效——这一条**不是缺陷**，已排除。

### F3 · `sync_sources action='diff'` 把「这次没动过」的文件报成「这一版新增」

**症状**：对某个具体文件问代际 diff，若归档里读不到旧内容，输出直接断言：

```
(added in this version — no previous content)
```

**为什么是缺陷**：反向增量归档**只归档被改写或删除的旧文件**（`Capture` 里那句
`if (change.Kind == Added) continue`）。所以「归档里没有」有**两种完全相反**的成因：

1. 这个文件是这一版**新增**的；
2. 这个文件**压根没被这一版动过**。

而 `sync_sources` 的主用途恰恰是回答「更新后到底改了什么」。把二者混为一谈，等于对最核心的问题
给出**反向的事实**。实测在 fixture 上稳定复现：v1→v2 同步中未被触碰的 `Untouched.cs`
被报成「v2 新增」。

**改法**：

- `SourceHistoryStore` 新增 `bool? WasPresentAt(source, versionId, relativePath)`。
  真相源是 `hashes.json`——它存的是**同步前那棵树的完整哈希表**，表里有即「那时就在」。
  返回 `null` = 哈希表读不出来，调用方应表述为「无法判定」，不替它选一个。
- `SyncSourcesTool` 据此分三态输出：
  - `true` → `(unchanged in this version — it already existed at this point and this sync did not touch it; the archive only keeps files a sync overwrote or removed)`
  - `false` → `(added in this version — no previous content)`
  - `null` → 明说两者分不出来，并指向 `action='diff'` 不带 `file` 看这一版真正改了哪些文件。

**回归**：`SyncSourcesUntouchedFileTests.cs`（4 条）——未触碰不报新增 / 真新增仍报新增 /
被改文件仍出行级 diff / 路径分隔符形式不翻转判定。

### F4 · 模糊匹配参数没有长度闸，长输入既拖垮进程又原样回灌调用方上下文

**症状**：`locate.query` / `inspect.name` / `trace.symbol` 会与索引里**每一个**类型名、成员名、
defName 逐一打分，代价 O(语料 × 串长)。实测一条 **100 KB** 的 query：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 耗时 | **77.85 s**（210% CPU） | **0.03 s** |
| 返回体积 | **100 130 字符** | **530 字符** |

返回体积的来源是零命中消息把那 100 KB **原样回显**进 `No results for '…'`。

**为什么是缺陷**：两重放大器。其一，一次误用就能让服务端烧掉一分多钟；其二，错误消息按
「输入多大、输出就多大」把等量垃圾塞回调用方上下文——而调用方是上下文受限的 LLM。
语料里最长的符号名也就几十个字符，越过闸的**一定**是误用（多半是把整段代码粘进了 query）。

**改法**：

- `ToolArgs.MaxFuzzyQueryLength = 256` + `GetRequiredFuzzyString(...)`：越界立刻抛
  `ToolArgumentException`，消息说清「限多少 / 为什么 / 该改成什么」，并指路
  `search_regex`（真正该用来按内容匹配的工具）。
- `ToolArgs.ForEcho(value, maxLength = 120)`：回显一律截断，附
  `… (N chars total)`。`LocateTool` 的零命中消息改走它。
- `LocateTool` / `InspectTool` / `TraceTool` 主参数切到 `GetRequiredFuzzyString`。

**边界实测**：恰好 256 字符仍正常处理（0.43 s / 269 字符返回），回显截断为 `… (256 chars total)`。

**回归**：`ToolArgsTests.cs` 新增 4 条——越界拒绝且消息可自我纠正、拒绝消息本身不得成为放大器
（不回显原串、总长 < 1000）、恰好卡上限仍接受、`ForEcho` 截断/不截断两态。

### F5 · `inspect` 截断合并 XML 后，把调用方指向一份不含被截内容的文件

**症状**：def 模式返回的是**沿整条 `ParentName` 链合并后**的 XML。超过 300 行时截断，提示写：

```
(Full XML: 812 lines, use read_code on file path above)
```

**为什么是缺陷**：`File:` 那一行指的是**子 def 自己那份未合并的源文件**。照着提示走，拿回来的是
另一份文档，而且缺的正是继承来的字段——**inspect def 模式唯一的存在理由**。合并结果不对应磁盘上
任何一个文件，所以此前**根本没有**任何办法拿到被截掉的中段。

**改法**（用到了「工具签名可改」这条授权）：

- 新增参数 `xmlStartLine`（1-based）。传了就渲染一段 250 行的连续窗口，并给出下一次该填的值；
  走到尾则明说 `End of the merged XML`，不再给一个指向空白的续读值。
- 不传时保留头 200 + 尾 50 的形状（首屏看 def 最有用的是开头字段与结尾结构），但提示改成
  指回 inspect 自己，并**明说** `File:` 那行只有未合并的部分。
- 截断标记同时给出被截区间（`Truncated N lines: 201-762`）。

**回归**：`InspectXmlPagingTests.cs`（5 条）——短 XML 不给续读提示 / 截断提示指回 inspect 且不再提
`read_code on file path above` / 续读拿到的确实是被截的中段 / 到尾说到尾 / 越界起点夹到末行。

### F6 · 解释不了的 `limit` 被静默换成默认值

**症状**：`limit:"many"` → `ToolArgs.GetInt` 解析失败 → 返回 fallback（10），输出里零痕迹。
`true` / `{}` / 多元素数组同理。

**为什么是缺陷**：与拼错的 `scope` **不对称**，因为两者退回的方向相反。scope 退回全域给出的是
**超集**，调用方不会少东西，一行提示足够；而 limit 退回默认给出的是**子集**——调用方要 100 条、
拿到 10 条、且 10 这个数它自己从没写过。「静默给少」在只读工具返回文本的调用方那里会直接沉淀成
「一共就这么多」。

**改法**：`ScopeArgs.GetDisplayLimit` 新增 `TryCoerceLimit`，解释不了就抛 `ToolArgumentException`，
消息说清收到了什么（类型化描述，长串经 `ForEcho` 截断）以及可接受的取值。单元素数组仍按
`ToolArgs` 的既有口径认下来（客户端序列化的常见抖动）。

**回归**：`ToolArgsTests.cs` 新增 7 条（5 条 Theory + 单元素数组 + 拒绝消息不放大）。

### F7 · `trace mode:'inheritors'` 只返回直接子类，却对外称「子类树」

**症状**：`GetInheritors` 只查一层 `_inheritorsMap`，没有传递闭包。而工具描述、输出表头、
README 三处都称其为「子类/实现类树」。

**为什么是缺陷**：RimWorld 的类型层级普遍三四层深。实测
`CompApparelVerbOwner` → `CompApparelVerbOwner_Charged` → `CompApparelReloadable`：
问「`CompApparelReloadable` 是不是 `CompApparelVerbOwner` 的子类」，修复前的答案是**不是**——
而这正是本 mode 最主要的用途。`ThingComp` 的真实后代数从直接子类涨到 **403**（最深 4 层）。

**改法**：

- `GetInheritors` 改为逐层 BFS 走到底，带环保护（短名归并后同名类型跨命名空间可成环）与
  深度护栏 `MaxInheritorDepth = 24`。回传 `depths` 供展示层用。
- **浅的排前面**：截断时留下的必须是直接子类，而不是字母序恰好靠前的某个曾孙。
- 每条标注 `[direct]` / `[depth N]`——拍平成一列后，这两者在「该覆写哪一层方法」上含义完全不同。
- 表头的两个数**只描述列出来的这些条目**（`Listed below: 6 (6 direct, deepest 1 level(s) down)`）。
  拿展示切片当整棵树的统计量、或反过来，都会造出一个「看起来像结论」的假数字——正是本轮要清的那类。
  （这一条是我自己第一版改动引入的，live 复核时发现并当场修掉。）

**回归**：`TraceInheritorsDepthTests.cs`（7 条）。

### F8 · `trace inheritors` 把「索引里没有这个名字」说成「它没有子类」

**症状**：两种情形共用一句 `No subclasses of 'X' found in scope '...'`。

**为什么是缺陷**：下一步完全不同。前者要去核对拼写（多半拼错了，或那个源没配进来），后者已经
是答案。说成同一句话，调用方会拿着一个根本不存在的名字继续往下查。

**改法**：`SourceIndexer.IsKnownType`（全名 + 短名两条路都试）分流：

- 不在索引 → `No type named 'X' is in the index, so this is not evidence that it has no subclasses.`
  并指路 `locate`，同时点明本 mode 只解析 C# 类型名。
- 在索引、无子类 → `'X' is indexed, and nothing in scope '...' derives from it (this is an answer,
  not a lookup failure).`

**回归**：同 `TraceInheritorsDepthTests.cs`。

### F9 · `search_regex` 三处静默削减命中集，而它自己承诺「没有尾注即完整」

工具 Description 原文：*"both cuts are always stated in a trailing note, so output without that note
is the complete match set."* 实际有**四处**会破这个承诺：

| # | 路径 | 修复前的表现 |
| --- | --- | --- |
| a | 正则在单个文件上超时（1 s，灾难性回溯） | `catch { }` 吞掉。该文件被弃在半路，预览已进结果、而 `matchesByFile` 那行在 `try` 尾部走不到，于是 `+N more in this file` **凭空消失** |
| b | 文件读不开（IO / 权限） | 同一个 `catch { }` 吞掉，整个文件静默跳过 |
| c | 单文件扫到 `MaxLinesScannedPerFile`（20000 行）就 break | 一个字都不说 |
| d | 截断时把 `allFiles.Count` 印成 "matching files" | 扫描早已在命中上限处停下，那个数只是**已扫预览里的去重文件数**，比真实值小一到两个数量级，而调用方会拿它当结论 |

另有 e：命中上限截断只劝「narrow the pattern or the scope」，从不提 `limit:'all'`——把唯一能立刻
多拿一倍结果的旋钮藏了起来。

**改法**：

- `SearchRegexAsync` 返回值加 `RegexScanDiagnostics`（候选文件数 / 超时文件数 / 不可读文件数 /
  触到行上限的文件数 / 行上限值）。裸 `catch { }` 拆成按异常类型计数，不再吞。
- 展示层新增 `[Incomplete scan: ...]` 尾注，逐项说明。
- 截断状态下的文件数改述为「已扫预览里出现的去重文件数，不是命中文件总数」；未截断时才用原措辞。
- 截断且未用满硬上限时，出路里补上 `limit:'all'`；已经要过 `'all'` 的不再劝一次。
- 零命中且传了 `fileFilter` 时回显该过滤器与它留下的候选文件数，候选为 0 时直接点明
  「是过滤器而不是 pattern 把结果清空的」。

**回归**：`SearchRegexHonestyTests.cs`（8 条）。

### F10 · `field:` / `method:` 前缀根本不按成员种类过滤

**症状**：README 的前缀表写着 `field:` =「只搜字段/属性」、`method:` =「只搜方法」。实现里这两个
前缀唯一的作用是**关掉 C# Types / XML Defs 两段**；`SearchMembersByKeywords` 压根没有成员种类
参数。实测 `field:Tick`：Methods 组 5 条 100%，Fields 组**只有 1 条**。

**为什么是缺陷**：挤占发生在**取回**阶段——候选按分数取 `limit.Scale(3)` 条，不分种类。语料里
名为 `Tick` 的方法数量压倒性多于字段，于是方法把配额吃光。用一个文档承诺「只搜字段」的过滤器去
枚举字段，实际只捞到 1 条，且 `limit:'all'` 也救不回（配额放大后取回仍不分种类）。

**改法**：`SearchMembersByKeywords` 新增 `memberKinds` 参数，过滤发生在取回层（筛在展示层等于
先让方法把配额吃光）。`LocateTool` 按前缀映射：`method:` → `Method`，`field:`/`property:` →
`Field` + `Property`。不传前缀时不筛，三类照旧全给。

**回归**：`LocateFilterPrefixTests.cs`。

### F11 · `type: X`（冒号后带空格）让整段结果静默消失

**症状**：`type: CompShield` 分词后是 `["type:", "CompShield"]`。空的 filter 值此前照样被当成
「用户指定了过滤词」，把该段搜索词覆盖成空串——**C# Types 段整段不见**，读起来就是「这个类型不
存在」。而 `type:CompShield` 正常返回 100%。

**为什么是缺陷**：冒号后带空格是人写查询时极常见的写法，触发条件一点也不刁钻，后果却是判据①
（作用域内有，被说成没有）。

**改法**：`QueryParser` 在 filter 值为空且前缀已知时**绑定到下一个 token**，与无空格写法等价；
后面没有 token 的光杆前缀则视同未指定（设了等于用空串去搜，恒零命中），并置
`HadEmptyFilterValue` 让工具层说出「它被忽略了」。

**回归**：同上，含「两种写法正文逐字相同」的等价性断言。

### F12 · 认不出的前缀被静默当成关键词

**症状**：`member:CompTick` → `No results`；`method:CompTick` → 144 条。同一个符号，一个说不
存在、一个说有一百多处，差别全在那个没被识别的前缀上，而返回里毫无线索。

**为什么是缺陷**：整个 token 连前缀一起当关键词这条**解析行为本身是有意的**（`QueryParserTests`
钉着），问题只在**无声**。本仓库对同族问题已有明确惯例：拼错的 scope 有 `UnresolvedNotice`，
`sync_sources` 的 `action`/`granularity`/`sources` 拼错一律报错——查询前缀是同一家族里唯一
还静默的入口。

**改法**：`ParsedQuery.UnknownPrefixes` 记下认不出的前缀，`LocateTool` 在返回末尾追加
`_'member:' is not a query filter, so it was matched as ordinary search text. Known filters: …_`。
解析行为不变，只补提示。

**回归**：同上。

### F13 · `trace` 的 `limit` 说明沿用了模糊工具的文案（自查漏修）

### F14 · `inspect` def 模式的父链解析失败时静默产出「半份」合并 XML

> 由并行审计工作流提名、经对抗式复核确认为 **high**。

**症状**：三种情形渲染得**逐字同形**：

1. 这个 def 本来就没有父；
2. 父已经合进来了；
3. 父找不到，所以少了半份。

因为父 def `Lookup` 返回 null 时 `while` 循环直接结束，而 `CleanupMetadata` 又把 `ParentName`
属性删掉——**父缺失不留任何痕迹**。

**为什么是缺陷**：工具描述原话是 *"Def mode returns the XML merged down the whole ParentName
chain — the complete effective definition, which no single XML file contains"*。调用方据此把
半成品当完整生效定义。实测 `Vethara_Hediff_PsychicWound`（`ParentName="InjuryBase"`，而本轮语料
里没有 vanilla XML Defs）：返回里没有 `hediffClass`、也没有 Linked C# Types 段——两者本该从
`InjuryBase` 继承而来。调用方会由此断定「该 hediff 不关联任何 C# 类」，然后去补一个根本不缺的字段。

**改法**：

- `XmlInheritanceHelper` 新增 `DefInheritanceTrace`（走过的链 / 未解析的父名 / 是否触到深度护栏 /
  是否成环）与 `ResolveDefXmlWithTraceAsync`。原先三处静默 `break` 全部改为记录中断原因。
- `InspectTool` 固定输出一行链状态：完整时 `Inheritance chain: A <- B`，无父时明说
  `none (this def declares no ParentName)`，中断时给**警告**并指出下一步（换 `scope:'all'`；
  仍找不到则那个源没配进 config）。

**实测对照**（修复后）：

- `Vethara_Hediff_PsychicWound` → `**Warning: parent 'InjuryBase' was not found in scope 'all',
  so the XML below is NOT the complete effective definition …**`
- `Vethara_Hediff_RegenStatus` → `Inheritance chain: Vethara_Hediff_RegenStatus <-
  Vethara_Hediff_BenignBase`（`hediffClass` / `isBad` 等四个字段的真实来源就此可见）

**回归**：`InspectInheritanceChainTests.cs`（5 条），含「三种情形两两可区分」这条直指缺陷本体的断言。

### F15 · C# 大纲丢弃全部成员修饰符

> 同上，工作流提名 + 复核确认为 **medium**。

**症状**：`private` 与 `public`、`static` 与实例、`const` 与可写字段渲染成逐字相同的一行。

**为什么是缺陷**：`RoslynHelper.FormatParameter` 上方的注释**自己**写明了判据——「大纲的用途就是

**回归**：`OutlineModifierTests.cs`（4 条）。

### F16 · `read_code` 的四条「说不清自己做了什么」的返回

> 工作流 `read_code` 维度提名，对抗式复核确认为 **medium**×3 + **low**×1。四条并成一轮改，
> 因为都落在同一个 `ResolvePath` / 错误分支上。

**a · `className` 传错时谎称成员不在这个文件里**

`{"path":"Pawn.cs","methodName":"ExposeData","className":"NoSuchClass"}` 回的是
`Member 'ExposeData' not found in Pawn.cs`。`className` 只是个**过滤器**，过滤后候选归零与
「文件里根本没有这个成员」被折叠成同一句话，而这句话只点 `methodName`、完全不提 `className`。
调用方读到它会直接断定 Pawn 没有 override `ExposeData`（它在 4543 行），据此做出错的存档/序列化
判断——这正是前几轮整改过的「把过滤结果说成不存在」在 `read_code` 上的残留。

改法：`TargetNotFound` 且 `className` 非空时，不带过滤再问一次成员声明在哪几个类型上
（新增 `RoslynHelper.FindMemberOwnersAsync`）。实测：
`'ExposeData' does exist in Pawn.cs, but not in a type named 'NoSuchClass'. It is declared in: Verse.Pawn (line 4543). Drop className, or pass one of those.`

**b · 传目录被报成「文件不存在，去 locate 找」**

`/home/user/Assembly-CSharp` 是本服务**自己的已索引源根**，却被回成 `File not found`。调用方
照做只会拿到一堆文件名，仍不知道自己传的是目录；正解是同一台 server 上的 `list_directory`，
一次 `Directory.Exists` 就能判出来。改法：`ResolvePath` 前置目录判定，回
`'…' is a directory, not a file. List what is in it with rimworld-searcher__list_directory…`。

**c · not-found 只回显基名，丢掉调用方给的整条路径**

`/home/user/Assembly-CSharp/../../etc/passwd` 回的是 `File not found: 'passwd'`。于是
「路径写错了」和「这个文件没进索引」在返回里长得一模一样，无从分辨该改路径还是该改 `scope`。
改法：原样回显整条 path，并按输入是否为绝对路径分叉措辞（`that path does not exist on disk,
and no indexed file goes by that name either` / `no indexed file goes by that name`）。

**d · 裸行模式只印基名；scope 内同名文件静默几选一**

`methodName` / `extractClass` 两个模式印 `// File: <绝对路径>`，裸行模式只印
`// Pawn.cs (lines 1-5 of 4740)`。而 `path` 支持传基名，`SourceIndexer.GetPath` 在多份同名
文件里按 scope 排序**静默**取第一个（源码注释自承「Ratkin 与 vanilla 同名 .cs 之类」）。
两者叠加的后果：调用方以为读的是 vanilla 原版，实际读的是某 mod 的覆盖版，据此断言原版行为。
改法：裸行头部改印解析后的绝对路径；新增 `SourceIndexer.GetPathsByName`，scope 内命中 >1 份
时追加一行 `note: N files share this name in scope '…'; reading the highest-priority one. The others: …`。

**e · 出错当场的参数清单漏了 `scope`**

`ToolArgSpec` 第三段是调用方在参数错误现场唯一看得到的一份参数表，其余 6 个工具都写了
`scope`，只有 `read_code` 漏了——而它恰恰是最依赖 scope 的：`path` 传基名时正是 scope 决定
读哪个源。补齐并加一句「scope decides which source wins when several have a file of this name」。

**回归**：`ReadCodeHonestyTests.cs`（8 条）。另外两条既有测试断言的是旧行为（裸行头部印基名），
按新契约改断言。

### F17 · 大纲折叠掉的成员在整套 API 下没有任何取全途径

> 工作流 `inspect` 维度提名，复核确认为 **low**；实际改动落在 `inspect` 的工具签名上，
> 属用户裁定「全部放开，含参数语义与工具签名」的范围内。

**症状**：`inspect Pawn` 的大纲三类各折叠到 40 条，折叠行写
`... +78 more properties not shown (find one by name with locate, or read the full declaration with read_code extractClass)`。

**为什么是缺陷**：给的两条出路对触发折叠的大类型**都不成立**。① `locate` 只能按已知名字找成员，
而调用方恰恰是**不知道剩下 78 个叫什么**才来看大纲的，「find one by name」在「我想知道有哪些」
这个用意下是循环论证；② `read_code extractClass` 的上限是 `MaxLineCount = 2000` 行，而
`Verse/Pawn.cs` 有 4740 行——照做会先烧掉 2000 行源码的 token，再收到一次「已截断，改用
methodName」，仍然没拿到成员表。`inspect` 自身此前没有 `limit`
（schema 只有 `name`/`defType`/`xmlStartLine`/`scope`），`GetClassOutlineAsync` 的
`maxMembersPerKind` 是常量默认值、`InspectTool` 从不传。也就是说被折叠的 206 个成员**取不到**，
而输出写得像有。

**改法**：给 `inspect` 补 `limit`（复用其余工具的 `'all'` 语义与同一套非法值校验），折叠行改指
`limit:'all'`。这里的 `'all'` 必须是**真无限**，不能沿用 `ScopeArgs.HardLimit = 200`——单个类型
成员数超过 200 是常态（`Pawn` 就有 326 个）。

**实测对照**（`Pawn`）：默认 6558 字符、三条折叠行均指向 `limit:'all'`；`limit:'all'` 出
17178 字符、零折叠行、326 个成员全在。对照 `read_code extractClass Pawn` 的 43097 字符**且仍被
截断**——新出路比旧出路便宜 60%，且真的拿得到。

**回归**：`InspectOutlineLimitTests.cs`（5 条，含「`'all'` 越过 HardLimit」与「非法值报错」两条
边界）。`OutputVolumeCapTests.Outline_FoldLineNamesTheWayToGetTheRest` 断言的是旧折叠文案，
按新契约改断言。

### F18 · `list_directory` 三处：不排序、无法翻页、拒绝时不给合法根

> 工作流 `list_directory` 维度提名，复核确认为 **medium**×2 + **low**×1。

**a · 目录项完全不排序，截断后是文件系统顺序下的任意子集**

原先直接吃 `Directory.EnumerateFileSystemEntries` 的产出顺序，目录与文件混排
（`Properties/`、`obj/` 散落在文件之间）。默认 `limit=100` 而 `Verse` 有 **1755** 项时，
调用方拿到的 100 条是任意一段——它既无法据此断言「`Pawn_HealthTracker.cs` 不在这个目录」
（实际在，只是没进这 100 条），也无法预判把 limit 调到 300 会补上哪些。
改法：截断**之前**排序（先目录后文件、各自 `OrdinalIgnoreCase`）。截断语义随之变成
「按名序的前 N 个」，缺席才是可推理的；顺带让「先看有哪些子目录再下钻」不必整段扫读。

**b · 顶到 1000 上限时，剩余条目在任何参数组合下都取不到**

`Verse` 1755 项，工具无分页，另外 755 条**不存在任何取法**。而脚注给的两条替代路径都是
死路：①「list a deeper subdirectory」——被略去的 747 个正是 `Verse` **顶层文件**，8 个子目录
里一个都没有；②「use search_regex to filter this one by name/extension」——`search_regex`
的 pattern 匹配的是**文件正文行**不是文件名，`fileFilter` 是路径**后缀** `EndsWith`（写得出
`.cs`，写不出「限定在 /Verse 下」这个前缀条件），且它自己封顶 50 个文件。
改法：加 `offset` 参数；输出印**总条目数**与下一页该填的 offset。实测
`(1755 entries, showing the first 8) … [1747 more; pass offset=8 for the next page, or a larger limit]`，
`offset:1000` 正确落在 `showing 1001-1005`。

**c · 越界拒绝不说白名单里到底有哪些根**

错误只复述规则（「已索引源根及其下级」），一个具体路径都不给，而调用方读不到 `config.toml`
——冷启动时它没有任何合法输入可用。而同一份 `tools/list` 里 `locate` 的 `scope` 描述早就把真实
源名（`sources: vanilla, Vethara`）注了进去，这套注入机制是现成的，只有 `list_directory` 没用。
改法：`PathSecurity` 暴露只读 `Roots`；拒绝消息与工具 description 都报出真实根路径
（`skip_path_security` 打开时改说「检查已关闭」，否则调用方会照着一份并不生效的清单自我设限）。

**回归**：`ListDirectoryPagingTests.cs`（8 条）。三条既有测试断言的是旧脚注文案，按新契约改断言。

### F19 · `sync_sources` 两处误导 + 一处 schema 自相矛盾

> 工作流 `sync_sources` 维度提名，复核确认为 **medium**×2 + **low**×1。

**a · 「已配置但不可跟随」与「源名不存在」返回逐字相同的错误**

`sources:'vanilla'` 与 `sources:'NoSuchSource'` 都回
`No followable source matches 'X'. Followable sources: Vethara.`。而 `vanilla` 是 config 里
**真实存在**的源（每个查询工具的 scope 描述都写着 `sources: vanilla, Vethara`），只是没配
`assemblies` 故不可跟随。句中那句 `Followable sources: Vethara` 会被读成「配置里只有 Vethara
一个源」，与调用方刚从 scope 里读到的清单**直接矛盾**。两种情形的修复动作也完全不同：一个要
往 `[[sources]]` 补 `assemblies` 路径，一个只是改拼写。
改法：`SourceSyncService` 暴露 `AllSourceNames`，两种情形分两句话说。实测：
`'vanilla' is a configured source with no 'assemblies' path… Add assemblies = '…' to the matching [[sources]] block` /
`No configured source matches 'NoSuchSource'. Configured sources: vanilla, Vethara (followable: Vethara).`

**b · sync 成功后无条件推荐 `action='diff'`，而它 100% 会报错**

`source_history_depth=0` 时这次同步根本没归档，`diff` 是**确定性**失败——而 sync 正文刚说有
739 个文件变更，调用方追查不到，反过来还会怀疑这次 sync 是不是真的成功。服务端在印这句话时
已经知道 `History.Enabled == false`。改法：按该旗分支，未启用时改说「这一次没有归档，
下次同步前把 `source_history_depth` 设成 ≥1」。

**c · `version` 的 schema 只声明 string，描述却让传数字**

描述第一句是「A number counts backwards — 1 (or -1)」，照字面传 JSON 数字的调用会被会校验
`inputSchema` 的 MCP client 在**发出前**挡下，调用方拿到的是客户端层的类型错误而不是工具的
回答。服务端其实两种都收。同文件里 `limit` / `sources` 早已按「两种都收就两种都声明」对齐，
只有这里漏了。改法：`type = ["string", "integer"]`。

### F20 · 未知参数名被静默丢弃，返回里没有任何痕迹

> 工作流协议维度提名，复核确认为 **low**。

**症状**：`locate` 传 `bogusParam` 照常返回 2460 字符的正常结果，整份返回里没有一行提到它被忽略。

**为什么是缺陷**：服务端对参数名极宽容（别名吸收 + 大小写/下划线归一），调用方由此学到
「这台服务器对名字不挑」，于是把别的工具的参数类推过来是**必然**行为——`locate` 传 `defType`
（`inspect` 才有）、`trace` 传 `fileFilter`（`search_regex` 才有）。这些键一律被丢弃，而返回
逐字正常，调用方据此得出的结论是「我按 X 过滤后就这些」，实际是**未过滤**的全量前 N 条。
错误方向与本仓已经修过的 `sync_sources` 的 `granularity` 拼错完全同型，而那处早就建了
`_Ignored 'x': …_` 提示通道，唯独参数键这一层没有。

**改法**：`ITool` 加默认实现的 `ExtraAcceptedKeys`（schema 没声明、但各 getter 实际吸收的别名），
`ToolArgs.UnknownKeyNotice` 用「schema 属性名 ∪ 别名」做差集，在分发出口追加一行。提示只在
差集非空时出现，健康调用零开销、零额外 token。**合法别名不得被误报**——那比不提示更糟，
故 7 个工具各自声明了自己的别名集，并有一条回归逐个验证。

**实测**：`locate {"query":"Pawn","bogusParam":1}` →
`_Ignored unknown parameter(s): 'bogusParam'. rimworld-searcher__locate accepts: query, scope, limit._`；
`trace {..., "fileFilter":".cs"}` → 同构提示；`locate {"query":"CompShield","limit":3}` 无提示。

**回归**：`UnknownParameterNoticeTests.cs`（10 条，含别名与归一拼写的反向保险）。

## 五、审计中查证后**排除**的非缺陷

记在这里，避免日后重复调查、或被后续审计重新提出。

**5-1 · 主会话自查排除**

| 现象 | 结论 |
| --- | --- |
| 统一 diff 的上下文括号看起来错位 | 标准 LCS diff 行为，`git diff` 输出一致 |
| `version:1` 与默认值同义 | 语义自洽（「往回 1 代」） |
| fixture 结果里的 `+1 more (lower relevance)` | 无关的前缀模糊命中，非漏项 |
| fixture 的互斥条件目录只命中 1 处 | 文件级 shadowing 按 README 语义**正确**生效 |

**5-2 · 并行审计工作流提名后被对抗式复核驳回**

审计工作流共 19 个 agent（7 维度提名 40 条 + 12 批反驳式复核）全部完成。下列提名经复核**驳回**，
记在这里以免后续审计重复提出。

| 提名 | 驳回理由 |
| --- | --- |
| `locate` 多词查询恒零命中（提名 high） | 反证：`comp shield` → `CompShield` 93%、`pawn health tracker` → `Pawn_HealthTracker` 88%，机制论证不成立 |
| 抽象 def 被剥掉 `Abstract="True"` 标记 | 合并语义即「求生效定义」，抽象标记本就不参与生效结果 |
| `inspect` not-found 不给候选名 | README 明写 inspect 不做模糊匹配、locate 是唯一模糊入口；错误文本已点名下一步 |
| C# 模式下 `defType` 被静默忽略 | schema 描述已写明「it does not narrow type mode」 |
| `locate` 常用词的折叠行劝 `limit:'all'` 不划算 | 体积在 HardLimit 账内，非误导 |
| `trace inheritors` 折叠行的两条下一步不成立 | 论证建立在 e9678ad 之前的行为上，已随 F7 失效 |
