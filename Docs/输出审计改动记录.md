# RimSearcher 全量输出审计 · 改动记录

> 本文档是本轮「全量输出测试」的**唯一改动台账**。分支 `claude/rimsearcher-full-output-test-j52pb2`。
> 每条缺陷记：**症状 → 为什么这是缺陷（对调用方的后果）→ 改法 → 回归用例**。
> 判据：**LLM 调用方可用性优先**。一条输出只要会让调用方得出与事实相反的结论，就算缺陷——哪怕代码逻辑本身「没写错」。
>
> **五轮**：第一轮 F1–F20 治「**说错了**」（输出与事实相反）；第二轮起 R1–R30 + F21…F25 治
> 「**说对了但难读**」（结构 / 冗余 / token 浪费 / 跨工具不一致），判据同上——难读同样会让调用方
> 多花一轮或读岔。第二轮清「一行里说两遍」，第三轮清「**逐行**说 N 遍」（表头说过的话在每一条
> 结果行末尾再说一次）。
> 第四轮的来源是第二个审计工作流，挖的不再是逐行冗余而是**结构**问题（脚注长错位置、一行恒等于
> 两行前那一行、两个工具对「这份结果全不全」互相矛盾）；第四轮末已证逐行冗余见底。
> 第五轮因此换了入口：不再找冗余，改为**全语料文法自检**——拿 README 写明的共用文法逐条比对实际
> 印出来的行。本轮净体积是**加**的（+0.41%），买到的是「那个数到底数什么」这类推不出来的事实。
> 全语料 207 次调用累计：**620222 → 512035 字符（-17.4%）**，无一次调用的成败发生变化。

## 三、已确认并已修复的缺陷

### F1 · 配置加载失败后，服务照常启动并把「索引是空的」伪装成「这个符号不存在」

**怎么发现的**：我自己踩了。给探针传了**相对路径**的 `--config config-fixture.toml`，服务端按
自己的 exe 目录去解析，日志里写了 `Failed to load configuration | reason=file not found`,
然后——**照常启动**，零个源，并对每一条查询回一句体面的：

```
No results for 'FixtureComp' in scope 'all'.
```

**为什么是缺陷**：那行诊断只到了 **stderr**。启动阶段 `ServerLogger.OnLogAsync` 还没接上 MCP 通道，
而调用方是**只读工具返回文本**的 LLM。于是「服务器没有索引」被读成「代码里没有这个符号」——
这是**方向相反**的结论，且调用方没有任何线索能察觉。同一类症状还包括：配置加载成功但没配源、
配了源但源目录里一个可索引文件都没有。

**改法**：新增 `Sources/RimSearcher.Server/StartupHealth.cs`，两级提示：

- **阻塞级**（`BlockingReason`）：**每一次**工具返回都追加。因为这个会话里的**每一条**「没找到」
  都同样不可信，只说一次等于没说。文案：
  `**Warning: this server has no usable index, so the result above is not evidence of absence.**`
- **忠告级**（`Advisories`）：**每会话一次**（`Interlocked.Exchange` 保证），索引可用、重复即噪音。

`Program.cs` 在索引建完后判定三种阻塞成因并 `StartupHealth.Record(...)`；
`RimSearcher.cs` 在每次响应拼接时 `_startupNotice.Consume()`。

该提示**不受 `SuppressStalenessNotice` 影响**：那面旗关的是「源变了」这类时效提示，
而「索引根本是空的」与时效无关，任何工具都得照说。

配套：`SourceIndexer` / `DefIndexer` 各暴露 `IndexedFileCount`，用来判定「零文件」。

**回归**：`StartupHealthTests.cs`（6 条）——健康则静默 / 阻塞级每次都说 / 忠告级只说一次 /
忠告级不跨会话共享 / 阻塞级压过忠告级 / 空白理由视同健康。

### F2 · mod 布局取舍对调用方完全不可见

**症状**：`loadFolders.xml` 的条件目录选择、同名文件的**文件级 shadowing**（RimWorld 自己的
覆盖规则）都会让一部分文件**不进索引**。这些是工具**替调用方做的决定**，此前只写 stderr 日志。

**为什么是缺陷**：「搜不到某个 def」最可能的解释就是它所在的那份文件被 shadow 掉了。调用方看不到
这件事，就只能得出「这个 def 不存在」。

**改法**：并入 F1 的忠告级通道。`Program.cs` 把 `resolvedSources.Notes` 与
`resolvedSources.Shadowed.Count` 汇成 advisories，随本会话第一条工具返回捎出：
`**Note: the indexed source layout involved choices you cannot see from the results.**`

**回归**：同 `StartupHealthTests.cs`。

**注**：fixture 里那组「互斥条件目录」经 `search_regex` / `trace` 复核**只命中 1 处**，
即 shadowing 按 README 语义正确生效——这一条**不是缺陷**，已排除。

### F3 · `sync_sources action='diff'` 把「这次没动过」的文件报成「这一版新增」

**症状**：对某个具体文件问代际 diff，若归档里读不到旧内容，输出直接断言：

```
(added in this version — no previous content)
```

**为什么是缺陷**：反向增量归档**只归档被改写或删除的旧文件**（`Capture` 里那句
`if (change.Kind == Added) continue`）。所以「归档里没有」有**两种完全相反**的成因：

1. 这个文件是这一版**新增**的；
2. 这个文件**压根没被这一版动过**。

而 `sync_sources` 的主用途恰恰是回答「更新后到底改了什么」。把二者混为一谈，等于对最核心的问题
给出**反向的事实**。实测在 fixture 上稳定复现：v1→v2 同步中未被触碰的 `Untouched.cs`
被报成「v2 新增」。

**改法**：

- `SourceHistoryStore` 新增 `bool? WasPresentAt(source, versionId, relativePath)`。
  真相源是 `hashes.json`——它存的是**同步前那棵树的完整哈希表**，表里有即「那时就在」。
  返回 `null` = 哈希表读不出来，调用方应表述为「无法判定」，不替它选一个。
- `SyncSourcesTool` 据此分三态输出：
  - `true` → `(unchanged in this version — it already existed at this point and this sync did not touch it; the archive only keeps files a sync overwrote or removed)`
  - `false` → `(added in this version — no previous content)`
  - `null` → 明说两者分不出来，并指向 `action='diff'` 不带 `file` 看这一版真正改了哪些文件。

**回归**：`SyncSourcesUntouchedFileTests.cs`（4 条）——未触碰不报新增 / 真新增仍报新增 /
被改文件仍出行级 diff / 路径分隔符形式不翻转判定。

### F4 · 模糊匹配参数没有长度闸，长输入既拖垮进程又原样回灌调用方上下文

**症状**：`locate.query` / `inspect.name` / `trace.symbol` 会与索引里**每一个**类型名、成员名、
defName 逐一打分，代价 O(语料 × 串长)。实测一条 **100 KB** 的 query：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 耗时 | **77.85 s**（210% CPU） | **0.03 s** |
| 返回体积 | **100 130 字符** | **530 字符** |

返回体积的来源是零命中消息把那 100 KB **原样回显**进 `No results for '…'`。

**为什么是缺陷**：两重放大器。其一，一次误用就能让服务端烧掉一分多钟；其二，错误消息按
「输入多大、输出就多大」把等量垃圾塞回调用方上下文——而调用方是上下文受限的 LLM。
语料里最长的符号名也就几十个字符，越过闸的**一定**是误用（多半是把整段代码粘进了 query）。

**改法**：

- `ToolArgs.MaxFuzzyQueryLength = 256` + `GetRequiredFuzzyString(...)`：越界立刻抛
  `ToolArgumentException`，消息说清「限多少 / 为什么 / 该改成什么」，并指路
  `search_regex`（真正该用来按内容匹配的工具）。
- `ToolArgs.ForEcho(value, maxLength = 120)`：回显一律截断，附
  `… (N chars total)`。`LocateTool` 的零命中消息改走它。
- `LocateTool` / `InspectTool` / `TraceTool` 主参数切到 `GetRequiredFuzzyString`。

**边界实测**：恰好 256 字符仍正常处理（0.43 s / 269 字符返回），回显截断为 `… (256 chars total)`。

**回归**：`ToolArgsTests.cs` 新增 4 条——越界拒绝且消息可自我纠正、拒绝消息本身不得成为放大器
（不回显原串、总长 < 1000）、恰好卡上限仍接受、`ForEcho` 截断/不截断两态。

### F5 · `inspect` 截断合并 XML 后，把调用方指向一份不含被截内容的文件

**症状**：def 模式返回的是**沿整条 `ParentName` 链合并后**的 XML。超过 300 行时截断，提示写：

```
(Full XML: 812 lines, use read_code on file path above)
```

**为什么是缺陷**：`File:` 那一行指的是**子 def 自己那份未合并的源文件**。照着提示走，拿回来的是
另一份文档，而且缺的正是继承来的字段——**inspect def 模式唯一的存在理由**。合并结果不对应磁盘上
任何一个文件，所以此前**根本没有**任何办法拿到被截掉的中段。

**改法**（用到了「工具签名可改」这条授权）：

- 新增参数 `xmlStartLine`（1-based）。传了就渲染一段 250 行的连续窗口，并给出下一次该填的值；
  走到尾则明说 `End of the merged XML`，不再给一个指向空白的续读值。
- 不传时保留头 200 + 尾 50 的形状（首屏看 def 最有用的是开头字段与结尾结构），但提示改成
  指回 inspect 自己，并**明说** `File:` 那行只有未合并的部分。
- 截断标记同时给出被截区间（`Truncated N lines: 201-762`）。

**回归**：`InspectXmlPagingTests.cs`（5 条）——短 XML 不给续读提示 / 截断提示指回 inspect 且不再提
`read_code on file path above` / 续读拿到的确实是被截的中段 / 到尾说到尾 / 越界起点夹到末行。

### F6 · 解释不了的 `limit` 被静默换成默认值

**症状**：`limit:"many"` → `ToolArgs.GetInt` 解析失败 → 返回 fallback（10），输出里零痕迹。
`true` / `{}` / 多元素数组同理。

**为什么是缺陷**：与拼错的 `scope` **不对称**，因为两者退回的方向相反。scope 退回全域给出的是
**超集**，调用方不会少东西，一行提示足够；而 limit 退回默认给出的是**子集**——调用方要 100 条、
拿到 10 条、且 10 这个数它自己从没写过。「静默给少」在只读工具返回文本的调用方那里会直接沉淀成
「一共就这么多」。

**改法**：`ScopeArgs.GetDisplayLimit` 新增 `TryCoerceLimit`，解释不了就抛 `ToolArgumentException`，
消息说清收到了什么（类型化描述，长串经 `ForEcho` 截断）以及可接受的取值。单元素数组仍按
`ToolArgs` 的既有口径认下来（客户端序列化的常见抖动）。

**回归**：`ToolArgsTests.cs` 新增 7 条（5 条 Theory + 单元素数组 + 拒绝消息不放大）。

### F7 · `trace mode:'inheritors'` 只返回直接子类，却对外称「子类树」

**症状**：`GetInheritors` 只查一层 `_inheritorsMap`，没有传递闭包。而工具描述、输出表头、
README 三处都称其为「子类/实现类树」。

**为什么是缺陷**：RimWorld 的类型层级普遍三四层深。实测
`CompApparelVerbOwner` → `CompApparelVerbOwner_Charged` → `CompApparelReloadable`：
问「`CompApparelReloadable` 是不是 `CompApparelVerbOwner` 的子类」，修复前的答案是**不是**——
而这正是本 mode 最主要的用途。`ThingComp` 的真实后代数从直接子类涨到 **403**（最深 4 层）。

**改法**：

- `GetInheritors` 改为逐层 BFS 走到底，带环保护（短名归并后同名类型跨命名空间可成环）与
  深度护栏 `MaxInheritorDepth = 24`。回传 `depths` 供展示层用。
- **浅的排前面**：截断时留下的必须是直接子类，而不是字母序恰好靠前的某个曾孙。
- 每条标注 `[direct]` / `[depth N]`——拍平成一列后，这两者在「该覆写哪一层方法」上含义完全不同。
- 表头的两个数**只描述列出来的这些条目**（`Listed below: 6 (6 direct, deepest 1 level(s) down)`）。
  拿展示切片当整棵树的统计量、或反过来，都会造出一个「看起来像结论」的假数字——正是本轮要清的那类。
  （这一条是我自己第一版改动引入的，live 复核时发现并当场修掉。）

**回归**：`TraceInheritorsDepthTests.cs`（7 条）。

### F8 · `trace inheritors` 把「索引里没有这个名字」说成「它没有子类」

**症状**：两种情形共用一句 `No subclasses of 'X' found in scope '...'`。

**为什么是缺陷**：下一步完全不同。前者要去核对拼写（多半拼错了，或那个源没配进来），后者已经
是答案。说成同一句话，调用方会拿着一个根本不存在的名字继续往下查。

**改法**：`SourceIndexer.IsKnownType`（全名 + 短名两条路都试）分流：

- 不在索引 → `No type named 'X' is in the index, so this is not evidence that it has no subclasses.`
  并指路 `locate`，同时点明本 mode 只解析 C# 类型名。
- 在索引、无子类 → `'X' is indexed, and nothing in scope '...' derives from it (this is an answer,
  not a lookup failure).`

**回归**：同 `TraceInheritorsDepthTests.cs`。

### F9 · `search_regex` 三处静默削减命中集，而它自己承诺「没有尾注即完整」

工具 Description 原文：*"both cuts are always stated in a trailing note, so output without that note
is the complete match set."* 实际有**四处**会破这个承诺：

| # | 路径 | 修复前的表现 |
| --- | --- | --- |
| a | 正则在单个文件上超时（1 s，灾难性回溯） | `catch { }` 吞掉。该文件被弃在半路，预览已进结果、而 `matchesByFile` 那行在 `try` 尾部走不到，于是 `+N more in this file` **凭空消失** |
| b | 文件读不开（IO / 权限） | 同一个 `catch { }` 吞掉，整个文件静默跳过 |
| c | 单文件扫到 `MaxLinesScannedPerFile`（20000 行）就 break | 一个字都不说 |
| d | 截断时把 `allFiles.Count` 印成 "matching files" | 扫描早已在命中上限处停下，那个数只是**已扫预览里的去重文件数**，比真实值小一到两个数量级，而调用方会拿它当结论 |

另有 e：命中上限截断只劝「narrow the pattern or the scope」，从不提 `limit:'all'`——把唯一能立刻
多拿一倍结果的旋钮藏了起来。

**改法**：

- `SearchRegexAsync` 返回值加 `RegexScanDiagnostics`（候选文件数 / 超时文件数 / 不可读文件数 /
  触到行上限的文件数 / 行上限值）。裸 `catch { }` 拆成按异常类型计数，不再吞。
- 展示层新增 `[Incomplete scan: ...]` 尾注，逐项说明。
- 截断状态下的文件数改述为「已扫预览里出现的去重文件数，不是命中文件总数」；未截断时才用原措辞。
- 截断且未用满硬上限时，出路里补上 `limit:'all'`；已经要过 `'all'` 的不再劝一次。
- 零命中且传了 `fileFilter` 时回显该过滤器与它留下的候选文件数，候选为 0 时直接点明
  「是过滤器而不是 pattern 把结果清空的」。

**回归**：`SearchRegexHonestyTests.cs`（8 条）。

### F10 · `field:` / `method:` 前缀根本不按成员种类过滤

**症状**：README 的前缀表写着 `field:` =「只搜字段/属性」、`method:` =「只搜方法」。实现里这两个
前缀唯一的作用是**关掉 C# Types / XML Defs 两段**；`SearchMembersByKeywords` 压根没有成员种类
参数。实测 `field:Tick`：Methods 组 5 条 100%，Fields 组**只有 1 条**。

**为什么是缺陷**：挤占发生在**取回**阶段——候选按分数取 `limit.Scale(3)` 条，不分种类。语料里
名为 `Tick` 的方法数量压倒性多于字段，于是方法把配额吃光。用一个文档承诺「只搜字段」的过滤器去
枚举字段，实际只捞到 1 条，且 `limit:'all'` 也救不回（配额放大后取回仍不分种类）。

**改法**：`SearchMembersByKeywords` 新增 `memberKinds` 参数，过滤发生在取回层（筛在展示层等于
先让方法把配额吃光）。`LocateTool` 按前缀映射：`method:` → `Method`，`field:`/`property:` →
`Field` + `Property`。不传前缀时不筛，三类照旧全给。

**回归**：`LocateFilterPrefixTests.cs`。

### F11 · `type: X`（冒号后带空格）让整段结果静默消失

**症状**：`type: CompShield` 分词后是 `["type:", "CompShield"]`。空的 filter 值此前照样被当成
「用户指定了过滤词」，把该段搜索词覆盖成空串——**C# Types 段整段不见**，读起来就是「这个类型不
存在」。而 `type:CompShield` 正常返回 100%。

**为什么是缺陷**：冒号后带空格是人写查询时极常见的写法，触发条件一点也不刁钻，后果却是判据①
（作用域内有，被说成没有）。

**改法**：`QueryParser` 在 filter 值为空且前缀已知时**绑定到下一个 token**，与无空格写法等价；
后面没有 token 的光杆前缀则视同未指定（设了等于用空串去搜，恒零命中），并置
`HadEmptyFilterValue` 让工具层说出「它被忽略了」。

**回归**：同上，含「两种写法正文逐字相同」的等价性断言。

### F14 · `inspect` def 模式的父链解析失败时静默产出「半份」合并 XML

> 由并行审计工作流提名、经对抗式复核确认为 **high**。

**症状**：三种情形渲染得**逐字同形**：

1. 这个 def 本来就没有父；
2. 父已经合进来了；
3. 父找不到，所以少了半份。

因为父 def `Lookup` 返回 null 时 `while` 循环直接结束，而 `CleanupMetadata` 又把 `ParentName`
属性删掉——**父缺失不留任何痕迹**。

**为什么是缺陷**：工具描述原话是 *"Def mode returns the XML merged down the whole ParentName
chain — the complete effective definition, which no single XML file contains"*。调用方据此把
半成品当完整生效定义。实测 `Vethara_Hediff_PsychicWound`（`ParentName="InjuryBase"`，而本轮语料
里没有 vanilla XML Defs）：返回里没有 `hediffClass`、也没有 Linked C# Types 段——两者本该从
`InjuryBase` 继承而来。调用方会由此断定「该 hediff 不关联任何 C# 类」，然后去补一个根本不缺的字段。

**改法**：

- `XmlInheritanceHelper` 新增 `DefInheritanceTrace`（走过的链 / 未解析的父名 / 是否触到深度护栏 /
  是否成环）与 `ResolveDefXmlWithTraceAsync`。原先三处静默 `break` 全部改为记录中断原因。
- `InspectTool` 固定输出一行链状态：完整时 `Inheritance chain: A <- B`，无父时明说
  `none (this def declares no ParentName)`，中断时给**警告**并指出下一步（换 `scope:'all'`；
  仍找不到则那个源没配进 config）。

**实测对照**（修复后）：

- `Vethara_Hediff_PsychicWound` → `**Warning: parent 'InjuryBase' was not found in scope 'all',
  so the XML below is NOT the complete effective definition …**`
- `Vethara_Hediff_RegenStatus` → `Inheritance chain: Vethara_Hediff_RegenStatus <-
  Vethara_Hediff_BenignBase`（`hediffClass` / `isBad` 等四个字段的真实来源就此可见）

**回归**：`InspectInheritanceChainTests.cs`（5 条），含「三种情形两两可区分」这条直指缺陷本体的断言。

### F16 · `read_code` 的四条「说不清自己做了什么」的返回

> 工作流 `read_code` 维度提名，对抗式复核确认为 **medium**×3 + **low**×1。四条并成一轮改，
> 因为都落在同一个 `ResolvePath` / 错误分支上。

**a · `className` 传错时谎称成员不在这个文件里**

`{"path":"Pawn.cs","methodName":"ExposeData","className":"NoSuchClass"}` 回的是
`Member 'ExposeData' not found in Pawn.cs`。`className` 只是个**过滤器**，过滤后候选归零与
「文件里根本没有这个成员」被折叠成同一句话，而这句话只点 `methodName`、完全不提 `className`。
调用方读到它会直接断定 Pawn 没有 override `ExposeData`（它在 4543 行），据此做出错的存档/序列化
判断——这正是前几轮整改过的「把过滤结果说成不存在」在 `read_code` 上的残留。

改法：`TargetNotFound` 且 `className` 非空时，不带过滤再问一次成员声明在哪几个类型上
（新增 `RoslynHelper.FindMemberOwnersAsync`）。实测：
`'ExposeData' does exist in Pawn.cs, but not in a type named 'NoSuchClass'. It is declared in: Verse.Pawn (line 4543). Drop className, or pass one of those.`

**b · 传目录被报成「文件不存在，去 locate 找」**

`/home/user/Assembly-CSharp` 是本服务**自己的已索引源根**，却被回成 `File not found`。调用方
照做只会拿到一堆文件名，仍不知道自己传的是目录；正解是同一台 server 上的 `list_directory`，
一次 `Directory.Exists` 就能判出来。改法：`ResolvePath` 前置目录判定，回
`'…' is a directory, not a file. List what is in it with rimworld-searcher__list_directory…`。

**c · not-found 只回显基名，丢掉调用方给的整条路径**

`/home/user/Assembly-CSharp/../../etc/passwd` 回的是 `File not found: 'passwd'`。于是
「路径写错了」和「这个文件没进索引」在返回里长得一模一样，无从分辨该改路径还是该改 `scope`。
改法：原样回显整条 path，并按输入是否为绝对路径分叉措辞（`that path does not exist on disk,
and no indexed file goes by that name either` / `no indexed file goes by that name`）。

**d · 裸行模式只印基名；scope 内同名文件静默几选一**

`methodName` / `extractClass` 两个模式印 `// File: <绝对路径>`，裸行模式只印
`// Pawn.cs (lines 1-5 of 4740)`。而 `path` 支持传基名，`SourceIndexer.GetPath` 在多份同名
文件里按 scope 排序**静默**取第一个（源码注释自承「Ratkin 与 vanilla 同名 .cs 之类」）。
两者叠加的后果：调用方以为读的是 vanilla 原版，实际读的是某 mod 的覆盖版，据此断言原版行为。
改法：裸行头部改印解析后的绝对路径；新增 `SourceIndexer.GetPathsByName`，scope 内命中 >1 份
时追加一行 `note: N files share this name in scope '…'; reading the highest-priority one. The others: …`。

**e · 出错当场的参数清单漏了 `scope`**

`ToolArgSpec` 第三段是调用方在参数错误现场唯一看得到的一份参数表，其余 6 个工具都写了
`scope`，只有 `read_code` 漏了——而它恰恰是最依赖 scope 的：`path` 传基名时正是 scope 决定
读哪个源。补齐并加一句「scope decides which source wins when several have a file of this name」。

**回归**：`ReadCodeHonestyTests.cs`（8 条）。另外两条既有测试断言的是旧行为（裸行头部印基名），
按新契约改断言。

### F17 · 大纲折叠掉的成员在整套 API 下没有任何取全途径

> 工作流 `inspect` 维度提名，复核确认为 **low**；实际改动落在 `inspect` 的工具签名上，
> 属用户裁定「全部放开，含参数语义与工具签名」的范围内。

**症状**：`inspect Pawn` 的大纲三类各折叠到 40 条，折叠行写
`... +78 more properties not shown (find one by name with locate, or read the full declaration with read_code extractClass)`。

**为什么是缺陷**：给的两条出路对触发折叠的大类型**都不成立**。① `locate` 只能按已知名字找成员，
而调用方恰恰是**不知道剩下 78 个叫什么**才来看大纲的，「find one by name」在「我想知道有哪些」
这个用意下是循环论证；② `read_code extractClass` 的上限是 `MaxLineCount = 2000` 行，而
`Verse/Pawn.cs` 有 4740 行——照做会先烧掉 2000 行源码的 token，再收到一次「已截断，改用
methodName」，仍然没拿到成员表。`inspect` 自身此前没有 `limit`

`maxMembersPerKind` 是常量默认值、`InspectTool` 从不传。也就是说被折叠的 206 个成员**取不到**，
而输出写得像有。

**改法**：给 `inspect` 补 `limit`（复用其余工具的 `'all'` 语义与同一套非法值校验），折叠行改指
`limit:'all'`。这里的 `'all'` 必须是**真无限**，不能沿用 `ScopeArgs.HardLimit = 200`——单个类型
成员数超过 200 是常态（`Pawn` 就有 326 个）。

**实测对照**（`Pawn`）：默认 6558 字符、三条折叠行均指向 `limit:'all'`；`limit:'all'` 出
17178 字符、零折叠行、326 个成员全在。对照 `read_code extractClass Pawn` 的 43097 字符**且仍被
截断**——新出路比旧出路便宜 60%，且真的拿得到。

**回归**：`InspectOutlineLimitTests.cs`（5 条，含「`'all'` 越过 HardLimit」与「非法值报错」两条
边界）。`OutputVolumeCapTests.Outline_FoldLineNamesTheWayToGetTheRest` 断言的是旧折叠文案，
按新契约改断言。

### F18 · `list_directory` 三处：不排序、无法翻页、拒绝时不给合法根

> 工作流 `list_directory` 维度提名，复核确认为 **medium**×2 + **low**×1。

**a · 目录项完全不排序，截断后是文件系统顺序下的任意子集**

原先直接吃 `Directory.EnumerateFileSystemEntries` 的产出顺序，目录与文件混排
（`Properties/`、`obj/` 散落在文件之间）。默认 `limit=100` 而 `Verse` 有 **1755** 项时，
调用方拿到的 100 条是任意一段——它既无法据此断言「`Pawn_HealthTracker.cs` 不在这个目录」
（实际在，只是没进这 100 条），也无法预判把 limit 调到 300 会补上哪些。
改法：截断**之前**排序（先目录后文件、各自 `OrdinalIgnoreCase`）。截断语义随之变成
「按名序的前 N 个」，缺席才是可推理的；顺带让「先看有哪些子目录再下钻」不必整段扫读。

**b · 顶到 1000 上限时，剩余条目在任何参数组合下都取不到**

`Verse` 1755 项，工具无分页，另外 755 条**不存在任何取法**。而脚注给的两条替代路径都是
死路：①「list a deeper subdirectory」——被略去的 747 个正是 `Verse` **顶层文件**，8 个子目录
里一个都没有；②「use search_regex to filter this one by name/extension」——`search_regex`
的 pattern 匹配的是**文件正文行**不是文件名，`fileFilter` 是路径**后缀** `EndsWith`（写得出
`.cs`，写不出「限定在 /Verse 下」这个前缀条件），且它自己封顶 50 个文件。
改法：加 `offset` 参数；输出印**总条目数**与下一页该填的 offset。实测
`(1755 entries, showing the first 8) … [1747 more; pass offset=8 for the next page, or a larger limit]`，
`offset:1000` 正确落在 `showing 1001-1005`。

**c · 越界拒绝不说白名单里到底有哪些根**

错误只复述规则（「已索引源根及其下级」），一个具体路径都不给，而调用方读不到 `config.toml`
——冷启动时它没有任何合法输入可用。而同一份 `tools/list` 里 `locate` 的 `scope` 描述早就把真实
源名（`sources: vanilla, Vethara`）注了进去，这套注入机制是现成的，只有 `list_directory` 没用。
改法：`PathSecurity` 暴露只读 `Roots`；拒绝消息与工具 description 都报出真实根路径
（`skip_path_security` 打开时改说「检查已关闭」，否则调用方会照着一份并不生效的清单自我设限）。

**回归**：`ListDirectoryPagingTests.cs`（8 条）。三条既有测试断言的是旧脚注文案，按新契约改断言。

### F19 · `sync_sources` 两处误导 + 一处 schema 自相矛盾

> 工作流 `sync_sources` 维度提名，复核确认为 **medium**×2 + **low**×1。

**a · 「已配置但不可跟随」与「源名不存在」返回逐字相同的错误**

`sources:'vanilla'` 与 `sources:'NoSuchSource'` 都回
`No followable source matches 'X'. Followable sources: Vethara.`。而 `vanilla` 是 config 里
**真实存在**的源（每个查询工具的 scope 描述都写着 `sources: vanilla, Vethara`），只是没配
`assemblies` 故不可跟随。句中那句 `Followable sources: Vethara` 会被读成「配置里只有 Vethara
一个源」，与调用方刚从 scope 里读到的清单**直接矛盾**。两种情形的修复动作也完全不同：一个要
往 `[[sources]]` 补 `assemblies` 路径，一个只是改拼写。
改法：`SourceSyncService` 暴露 `AllSourceNames`，两种情形分两句话说。实测：
`'vanilla' is a configured source with no 'assemblies' path… Add assemblies = '…' to the matching [[sources]] block` /
`No configured source matches 'NoSuchSource'. Configured sources: vanilla, Vethara (followable: Vethara).`

**b · sync 成功后无条件推荐 `action='diff'`，而它 100% 会报错**

`source_history_depth=0` 时这次同步根本没归档，`diff` 是**确定性**失败——而 sync 正文刚说有
739 个文件变更，调用方追查不到，反过来还会怀疑这次 sync 是不是真的成功。服务端在印这句话时
已经知道 `History.Enabled == false`。改法：按该旗分支，未启用时改说「这一次没有归档，
下次同步前把 `source_history_depth` 设成 ≥1」。

**c · `version` 的 schema 只声明 string，描述却让传数字**

描述第一句是「A number counts backwards — 1 (or -1)」，照字面传 JSON 数字的调用会被会校验
`inputSchema` 的 MCP client 在**发出前**挡下，调用方拿到的是客户端层的类型错误而不是工具的
回答。服务端其实两种都收。同文件里 `limit` / `sources` 早已按「两种都收就两种都声明」对齐，
只有这里漏了。改法：`type = ["string", "integer"]`。

### F20 · 未知参数名被静默丢弃，返回里没有任何痕迹

> 工作流协议维度提名，复核确认为 **low**。

**症状**：`locate` 传 `bogusParam` 照常返回 2460 字符的正常结果，整份返回里没有一行提到它被忽略。

**为什么是缺陷**：服务端对参数名极宽容（别名吸收 + 大小写/下划线归一），调用方由此学到
「这台服务器对名字不挑」，于是把别的工具的参数类推过来是**必然**行为——`locate` 传 `defType`
（`inspect` 才有）、`trace` 传 `fileFilter`（`search_regex` 才有）。这些键一律被丢弃，而返回
逐字正常，调用方据此得出的结论是「我按 X 过滤后就这些」，实际是**未过滤**的全量前 N 条。
错误方向与本仓已经修过的 `sync_sources` 的 `granularity` 拼错完全同型，而那处早就建了
`_Ignored 'x': …_` 提示通道，唯独参数键这一层没有。

**改法**：`ITool` 加默认实现的 `ExtraAcceptedKeys`（schema 没声明、但各 getter 实际吸收的别名），
`ToolArgs.UnknownKeyNotice` 用「schema 属性名 ∪ 别名」做差集，在分发出口追加一行。提示只在
差集非空时出现，健康调用零开销、零额外 token。**合法别名不得被误报**——那比不提示更糟，
故 7 个工具各自声明了自己的别名集，并有一条回归逐个验证。

**实测**：`locate {"query":"Pawn","bogusParam":1}` →
`_Ignored unknown parameter(s): 'bogusParam'. rimworld-searcher__locate accepts: query, scope, limit._`；
`trace {..., "fileFilter":".cs"}` → 同构提示；`locate {"query":"CompShield","limit":3}` 无提示。

**回归**：`UnknownParameterNoticeTests.cs`（10 条，含别名与归一拼写的反向保险）。

## 三·续、第二轮：可读性专项（R1–R7）与由此带出的 F21

第一轮收敛后，剩下的问题不再是「说错了」而是「说对了但难读」。这一轮的判据同样是调用方可用性：
一行里同一件事说两遍、一维数据画成二维图、同一个概念每个工具一套写法——单条都不致命，但它们
**按结果行数线性放大**，且会把真正有信息的那几行淹掉。

**这一轮只做减法**：任何「补一句说明」的提议一律不采纳，那是第一轮的手段。

### R1 · `locate` 每行末尾那个能从符号名逐字推出来的文件名

**症状**：`- \`CompShield\` (100%) - CompShield.cs`。全量转储实测：2610 条结果行里 **2489 条（95%）**
的文件名就是 `<符号短名>.cs` 或 `<宿主类型>.cs`，共约 **58929 字符**纯冗余。

**为什么是缺陷**：这 95% 不承载信息，只把每行撑长；更要紧的是它把剩下 5% **真正有信息**的那些
（`PawnFilter` 在 `Dialog_BeginRitual.cs` 里、`PawnCount` 在 `ThingCountTracker.cs` 里）淹进噪声——
而那 5% 恰恰是调用方最需要看一眼的：符号不在同名文件里。

**改法**：`LocateTool.FileNote` —— 只在文件名**推不出来**时才印；同一类型分散在多个文件（partial /
多源各有一份）也算意外，照印并带 `+N more files`。Files 段去掉与全路径重复的基名。

**回归**：`OutputReadabilityTests` 的 `Locate_OmitsTheFileNameWhenItIsJustTheTypeNameDotCs` /
`Locate_KeepsTheFileNameWhenItIsNotDerivable` / `Locate_MemberRows_OmitTheDerivableFileName` /
`Locate_FileRows_DoNotPrintTheBaseNameBesideTheFullPath`。

### R2 · `inspect` 把线性的基类链画成 mermaid `graph TD`

**症状**：三层链渲染成 7 行 ~150 字符的 ```mermaid graph TD``` 块，每条边一行 `Child --> Parent`。

**为什么是缺陷**：C# 的基类链**恒为线性**，用二维图格式表达一维数据既费 token，又让读者得从箭头对里
自己重建先后顺序。同一个工具的 def 模式早在 F14 就在用一行式 `Inheritance chain: X <- Y`——
两处渲染同一个概念不该有两套写法。

**改法**：`InspectTool.LinearChain` 把 `(child, parent)` 对还原成一条线，输出
`Inheritance chain: Pawn <- ThingWithComps <- Thing <- Entity`（~45 字符）。命名空间在标题行已给过，
链上一律用短名——链读的是形状，短名也正是调用方转手喂回 `locate` / `read_code` 的写法。

**回归**：`Inspect_RendersTheBaseChainOnOneLine_NotAsAMermaidGraph` /
`Inspect_ChainLine_DoesNotRepeatIntermediateTypes` / `Inspect_TypeModeAndDefMode_UseTheSameChainWording`。

### R3 · 分隔的是空气的 `---`，以及三个结尾空行

**症状**：`inspect` 类型模式每份大纲后都追加一道 `---`，而绝大多数调用只有一份大纲；整份返回以
`\n\n\n` 收尾。

**为什么是缺陷**：结尾的横线与空行对 LLM 调用方是一个明确信号——「后面本来还有、被截断了」——
于是引出一次多余的重查。`read_code` 早有同款用例（`MultipleMatchingMembers_DoNotEndWithADanglingSeparator`），
`inspect` 漏了。

**改法**：分隔线画在两份大纲**之间**；结尾空行在 `ToolResult` 构造处 + 分发处拼装后各收一次
（漏一处等于没做）。

**回归**：`Inspect_SingleOutline_DoesNotEndWithADanglingSeparator` / `NoToolResponse_EndsWithBlankLines`
（后者一次性覆盖 6 个工具）。

### R4 · 同一个概念，五个工具五种写法

**症状**：「结果被截断了、这样能拿到更多」这一件事的五种渲染——

| 出处 | 原文 |
| --- | --- |
| `ScopeArgs.FoldLine`（locate/trace） | `... +N more (hint)` |
| `inspect` 大纲 | `... +N more X not shown (re-run inspect with limit:'all' …)` |
| `list_directory` | `... [N more; pass offset=X for the next page]` |
| `read_code` 行读 | `[N more lines available, use startLine=X]` |
| `read_code extractClass` | `[Truncated: 'Pawn' is 4729 lines, showing the first 2000. …]` |

**为什么是缺陷**：调用方每换一个工具就得重新认一次「这行是不是截断提示」。方括号 vs `... +`、
"available" vs "not shown" vs "Truncated" 三种词，没有一处是必要的差异。

**改法**：统一为 `... +N more <什么> (<怎么拿到>)`，`FoldLine` 的既有文法为准。
`not shown` 是 `more` 已经说过的话，删。

**回归**：`ReadCode_/ListDirectory_/InspectOutline_TruncationFootnote_FollowsTheSharedGrammar`
三条共用一个 `AssertSharedFootnoteGrammar`（正向断言文法 + 反向断言四个旧写法都不再出现）。

### R5 · `locate` 表头只说「查了什么」，不说「查到多少」

**症状**：`## 'CompShield'`，而 `trace` 是 `References to 'Pawn' (first 50 in scope 'all', …)`、
`list_directory` 是 `` `/path` (1755 entries, showing the first 8) ``。

**为什么是缺陷**：locate 是分段返回（C# Types / Members / XML Defs / Content Matches / Files），
不给分段计数，调用方只能自己数行才知道各段规模、是否需要调 `limit`。

**改法**：表头补 `— 5 C# types, 5 members`（正文先攒、表头最后拼）。单数不写成 `1 C# types`。

**回归**：`Locate_Header_StatesHowManyOfEachKind` / `Locate_Header_UsesSingularForOne`。

### R7 · `inspect` 表头与 `**Outline**` 之间的空行，class 有、interface 没有

**症状**：interface 走「无基类链」分支，`## C# Type: IExposable` 下一行直接是 `**Outline**`；
class 因中间隔着链那行而有空行。

**改法**：空行由 outline 循环统一发出，与有无链无关。

**回归**：`Inspect_HeaderToOutlineSpacing_IsTheSameWithOrWithoutAChain`。

### 实测收益

同一份 207 条调用矩阵，改前 / 改后：

| | 改前 | 改后 | 差 |
| --- | --- | --- | --- |
| 字符 | 620222 | 560132 | **-60090（-9.7%）** |
| 行 | 17098 | 16946 | -152（-0.9%） |
| 其中 locate 段（60 次调用） | — | — | **-59386（-28.2%）** |

**零信息损失校验**：逐调用比对结果行的反引号符号名集合，`locate` / `trace` / `inspect` /
`read_code` / `search_regex` 全部 **零漂移**——去掉的只有冗余，没有一条结果消失。

### F21 · `search_regex` 同一条查询给不同答案（可读性测量中带出）

**症状**：同一条 `search_regex` 连跑 6 次，实测给出 **3 种不同的文件集**。

**为什么是缺陷**：扫描是整张候选表满盘 `Parallel.ForEachAsync` + 命中上限一到就从委托头部
`return`，于是**哪些文件赶在上限前被扫到**取决于线程调度；`ConcurrentBag` 的枚举序是第二层不确定。
返回里那句 `showing the first N` 因此没有定义——调用方复查一遍拿到另一批文件，只能推断索引变了
或自己上次读错了。展示层此前已按文件名排序（掩盖了症状的一半：**顺序**稳了，**集合**没稳）。

**改法**（`SourceIndexer.SearchRegexAsync`）：
1. 按候选表顺序**分块**推进（`RegexScanChunkFiles = 256`），每块**整块**扫完再判上限——
   扫过的恒是候选表的一个前缀；
2. 每条命中带上所属文件在候选表里的序号，块内一律收下，最后按 `(文件序号, 行号)` 排序再截，
   不在扫描中途按上限丢弃（那等于让线程调度决定丢哪条）。

代价是命中上限那一刻最多多扫一块；实测最坏路径（全库无命中的全量扫描）0.44s，未见回归。

**回归**：`SearchRegex_SameQueryTwice_ReturnsTheSameAnswer`（同一 tool 实例连跑 5 次断言全等）/
`SearchRegex_RaisingTheLimit_OnlyAddsFiles_NeverSwapsThemOut`（截断选的是前缀，故放大 `limit`
只增不换）/ `SearchRegex_FilesAreListedInNameOrder`。

## 三·再续、第三轮：可读性专项（R8–R23）与由此带出的 F22

第二轮把「一行里说两遍」清掉之后，剩下的冗余全部集中在**逐行重复**上：一条判据在表头说过一次，
又在下面 200/400/600 行里各说一遍。这类冗余的特点是**单条看都很短**（`[direct]`、`[vanilla]`、
`Value: `、`(CompShield.cs)`），但它按结果行数线性放大，且**恰好长在正文的每一行末尾**——正是
读者扫读时视线扫过的地方。

判据仍是「删掉之后，调用方还能不能拿到同一个事实、走到同一个下一步」。本轮另有一条新增判据：
**排序键必须与印出来的东西是同一个**（F22）——它不省字符，但它决定「这个符号不在结果里」这句话
是否可信。

### R8 · `trace inheritors` 行末那个能从类型名推出来的 `(File.cs)`

**症状**：`- \`RimWorld.CompActivity\` [direct] (CompActivity.cs) [vanilla]`。

**为什么是缺陷**：与 R1 是同一条判据，只是 `locate` 改了、`trace` 没改——于是同一个服务器里两个
工具对同一件事有两套做法。实测 `trace.inh_big` 的 601 行里 **589 行（98%）**文件名可从类型短名逐字
推出；剩下 12 行是嵌套类型，按外层类型段同样可推。

**改法**：抽出 `SymbolRow.FileNote`（新文件），`locate` 与 `trace` 共用；分散在多文件时照印并带
`+N more files`。

### R9 · 逐行挂 601 遍的 `[direct]`

**症状**：`trace.inh_big` 的 601 行**全部**是直接子类，于是 `[direct]` 出现 601 次——把表头
`(403 in scope 'all', transitive)` 已经说过的话再说 601 遍。

**改法**：只标 `[depth N]`（N ≥ 2），直接子类不标；**且仅在这次结果里真有深层项时**，由表头补一句
`untagged = direct`——没有深层项时连这句都不必印，因为那时「全是直接子类」已由「一个标记都没有」
说清了。

### R10 · `trace usages` 组名前的 `[C#]` / `[XML]`

**症状**：`[C#] \`CompProperties_Shield.cs\` [vanilla]`。

**为什么是缺陷**：紧跟其后的文件名带着 `.cs` / `.xml`，说的是同一件事；而 `search_regex` 输出的是
同一种「文件名 + 缩进预览行」结构，从来没有这个前缀。

### R11 · `trace usages` 的文件分组之间不空行，`search_regex` 空

**症状**：两个工具输出的是同一种结构，`search_regex` 组间有空行、`trace` 没有，于是 `trace` 里
上一组的最后一条预览行与下一组的组名贴在一起，组的边界只剩缩进能看出来。

**改法**：组名之前恒有一个空行（首组除外，表头后面本就空着）。

**回归**：`TraceUsages_SeparatesFileGroups_TheSameWaySearchRegexDoes`。

### R12 · `search_regex` 表头把「扫描停了」说了第二遍，且单位含混

**症状**：`(first 50 in scope 'all', scan stopped at the limit)` —— `first 50` 本就含着「后面还有、
停在这儿了」，而末尾那行脚注会把同一件事再说一遍并给出下一步。另外这个 `50` 数的是**预览行**，
与未截断分支里的「命中数」不是一个量，两处都写成裸数字。

**改法**：表头只说 `first 50 previews in scope 'all'`，「扫描停下」交给末尾那行（那里同时给得出
下一步）。

### R13 · 「扫描停在上限处」一件事，`trace` 与 `search_regex` 两副样子

**症状**：

| 出处 | 原文 |
| --- | --- |
| `trace usages` | `[Preview lines truncated at limit 1 and scanning stopped there, raise limit to see more]` |
| `search_regex` | `[scanning stopped at the 1-preview cap — pass limit:'all' to raise the cap to 200, or narrow …]` |

方括号还是 R4 统一掉的旧写法——其余各工具的折叠脚注早已改用 `... +N more <什么> (<怎么拿到>)`。

**改法**：抽出 `ScopeArgs.ScanStoppedLine`，两个工具共用一句：
`... more matches exist (scan stopped at the N-preview cap; pass limit:'all' to raise the cap to 200,
or narrow the query or the scope)`。`limit` 已经是 `'all'` 时，「提 limit」这条出路不存在，改说
`scan stopped at the server cap of N preview lines` + 「缩小查询或范围」——**出路只印真的走得通的那条**。

**回归**：`TraceAndSearchRegex_ReportTheSameScanStopWithTheSameSentence`（正向断言共用文法 +
反向断言方括号旧写法不再出现）。

### R14 · `search_regex` 的 `[Incomplete scan: …]` 同样是方括号旧写法

**改法**：`... some files were not scanned in full (<哪些>; matches in the unscanned parts would not
be listed)`，与 R13 同形。

### R15 · 零命中时那句「是过滤器筛空的，不是 pattern」

**症状**：`with fileFilter '.zzz' (0 file(s) matched that filter — the filter, not the pattern, is
what emptied this)`。

**为什么是缺陷**：破折号后那句的全部内容，由同一个括号里紧挨着印出的那个 **`0`** 一步可推。而且
`CandidateFiles` 数的是 scope ∩ fileFilter 之后的量，scope 自己筛空时这句归因反而不准。

### R16 · `read_code` 正文之前的三行头

**症状**：`rc.method_enumvalue` 的整个 126 字符返回里，正文之前占了三行——

```
// Terrain                                     ← 调用方自己传的 methodName，原样回显
// File: /home/user/Assembly-CSharp/Verse/AltitudeLayer.cs
// Method, starts at line: 12
```

**为什么是缺陷**：第一行是参数回显（且紧接着的声明行里逐字写着同一个名字）；后两行说的是同一个
位置，而 `path:line` 是一行就说完的通用写法——同一个工具的**裸行模式**早就在用它。

**改法**：统一为一行 `// <Kind> <Name>[ in <Owner>] — <file>:<line>`。`extractClass` 走同一条文法
并印**全限定名**（同名类型分属不同命名空间时，返回里必须能看出取的是哪一个）；`Owner` 只在它与
成员名不同名时才印（构造函数的名字就是它所属类型的短名，`Constructor ZzA in Zz.ZzA` 里后半截
一个字都没多说）。

**回归**：`ReadCode_Member_LeadsWithExactlyOneLocationLine`（断言 `// ` 开头的行恰好 1 行）/
`ReadCode_ExtractClass_UsesTheSameLocationLineGrammar` / `ReadCode_Constructors_DoNotRepeatTheTypeNameAsTheOwner`。

### R17 · `// --- NEXT MATCH ---`

**症状**：同名成员多命中时，两条正文之间插 `// --- NEXT MATCH ---`。

**为什么是缺陷**：它只说「后面还有」，说不出**还有几条**；而末尾那条之后什么都没有，于是「是全了
还是被截了」在返回里无解。

**改法**：换成每条正文之前的 `[i/N]` 编号位置行——分段与进度由同一行承担，末尾也不再悬空。

**回归**：`ReadCode_MultipleMatches_ReplaceTheSeparatorWithNumberedLocationLines`。

### R18 · `extractClass` 报出的类行数把本服务自己加的注释行也数了进去

**症状**：`'Pawn' is 4729 lines`，而 `Pawn` 类自己不是 4729 行。

**为什么是缺陷**：位置注释是本服务加的一行、不是源码。调用方拿这个数去判断「值不值得整类取」
或「该按成员取哪几个」，数就得是类自己的行数；更实际的是，这些注释行还会**占掉 `MaxLineCount`
的额度**（要展示 2000 行正文，实际只展示了 1999 行）。

**改法**：`SourceLookupResult` 增设 `Body`（剔掉首行位置注释的正文），行数与截断都按 `Body` 算。

**回归**：`OutputVolumeCapTests` 补 `'Giant' is 2502 lines` / `... +502 more lines` / 围栏内行数
三条断言。

### R19 · 每行末尾那个一模一样的 ` [来源]`

**症状**：`locate.limit_200`（29898 字符）里 390 个 `[vanilla]` + 22 个 `[Vethara]` = **412 个标签
≈ 4120 字符 ≈ 正文的 14%**；`sr.basic` 50 行全是 `[vanilla]`（500 / 4721 = 10.6%）。

**为什么是缺陷**：`ScopeCatalog.ShowLabels => SelectedCount > 1` 判的是 **scope 里有几个源**，而不是
**这批结果实际落在几个源上**。实测 60 次 `locate` 调用的 80 个结果段里，**70 段是单一来源**——那 70
段里每一行的标签都写着同一个词。

**改法**：新增 `ScopeArgs.SourceLabeling`：`Of(rowSources)` 一次扫过实际要印的那些行，全同源就把
标签提到表头（`**C# Types** [vanilla]:`）、逐行不印；混源则维持逐行。**标签是移位不是删除**——
读者仍要能一眼看出这批结果来自哪儿；scope 已把源钉死时（`ShowLabels == false`）则一个都不印，
这条原有判据不受影响。`locate` 五段 / `trace usages` / `trace inheritors` / `search_regex` 共用。

其中 `locate` 的 Members 段要先把分组配额切出来再写表头——标签按**实际列出的那些行**判，而不是按
折叠前的全集。

**回归**：`Locate_UniformSourceSection_StatesTheSourceOnceOnTheHeader` /
`Locate_MixedSourceSection_KeepsThePerRowLabels`（反面）/ `Locate_SingleSourceScope_PrintsNoLabelAtAll` /
`TraceAndSearchRegex_AlsoHoistTheUniformSourceLabel`。

### R20 · `inspect` 无条件印文件名，绕过了 R1/R8 那条共用判据

**症状**：`C# Class: \`RimWorld.CompShield\` (CompShield.cs)`，以及链接类型段的 `- \`X\` (X.cs)` /
`- \`Y\` (not indexed)`。

**改法**：改走 `SymbolRow.FileNote`——三个工具至此是同一条判据。`(not indexed)` 由「没有文件注」
本身表达，不再单独印。

### R21 · enum 大纲每行的 `Value: `

**症状**：`inspect.enum`（`AltitudeLayer`）的 41 个取值，每行都以 `  Value: ` 开头。

**为什么是缺陷**：enum 分支是一条**专用的提前返回**，只渲染一种成员；上一行的 `Enum: Verse.AltitudeLayer
: byte` 已经把下面每一行是什么说完了。

> 本轮我据此把 class 大纲的种类前缀留了下来，理由是「那里混排多种成员」——**该事实认定有误**，
> class 大纲本就分块连续印。同一条判据（连续块的种类由表头说一次）第四轮由 R24 补作用于 class 分支。

**改法**：只留缩进 + 取值名 + 显式赋值（`Resetting = 7` 要留，查 enum 多半就是为了那个数）。

### R22 / R23 · `locate` 零命中时，同一条建议连说两遍

**R22**：`RetryWiderNotice`（「scope 收窄了，放宽再试」）与 out-of-scope 页脚（「这个符号在
scope 外的某源里有」）会同时出现，而后者已经把「去哪儿找」说得更具体。改为有页脚时不再印前者。

**R23**：过滤器清单 `(type:, method:, field:, def:)` 在「前缀没被识别」时由 `prefixNotice` 列过一遍
（那正是最该看到它的场合），紧接着的 `Try:` 行又列一遍。改为按前者是否出现二选一。

### F22 · `trace usages` 同一条查询给不同答案，且排序键与印出来的东西不是同一个（可读性测量中带出）

**症状**：与 F21 是同一类缺陷的**第二个实例**——F21 修的只是 `search_regex`。实测同一条
`trace mode:'usages' limit:1` 在不同轮次里给出过 `Stance_Warmup.cs` 与 `ThingDef.cs` 两个答案，
而返回里那句 `first 1` 于是没有定义。

第二个 facet：`trace usages` 与 `search_regex` 都**只印文件名**，却都**按完整路径排序**。读者看到的
是 C、C、G、D、S、T ——每进一个目录字母序就重来一遍，看上去根本没有顺序，于是「这个文件不在
结果里」是真没有、还是被截了，无从判断。

**改法**：
1. 新增 `SourceIndexer.InDisplayOrder`（先文件名、再完整路径兜同名），**扫盘与展示共用同一张表**；
   `search_regex` 的展示分组同步改用同一个键；
2. `trace usages` 按该顺序**分块**推进（`ScanChunkFiles = 256`），块内命中**一条不丢**全部收下，
   最后按 `(文件序号, 行号)` 排完序再截——不在扫描线程里抢配额（那等于让线程调度决定丢哪条）。

于是截断留下的恒是这张表的**前缀**，`limit` 调大只往后追加、不会把已经看到的文件换掉。

**回归**：`TraceUsages_TruncatedResult_IsTheSameEveryTime` /
`TraceUsages_RaisingTheLimit_OnlyAddsFiles_NeverSwapsThemOut` /
`GroupedHitTools_ListFilesInTheOrderTheyArePrinted`（两个工具共用一条断言）。

### 实测收益

## 三·三续、第四轮：R24–R28 + F23/F24

第三轮之后，「逐行重复」这条轴基本见底：对全语料做「某个 token 出现在本次结果 ≥80% 的行上」
的扫描，只剩一处命中——而那处是**真混源**的 `locate` 段，逐行印正是 R19 判定该保留的情形。

于是第四轮的来源换成了**第二个可读性审计工作流**（17 agent、52 条提名、7 条通过对抗式复核）。
它挖到的不再是逐行冗余，而是三类**结构**问题：一条脚注长在会被误读成属于上一组的位置、一行的
内容恒等于两行前那一行、以及**两个工具对「这份结果全不全」给出互相矛盾的表述**。

### R24 · `inspect` 大纲逐行的 `Property:` / `Field:` / `Method:`

**症状**：`  Property: public float Energy` × 96 行、`  Field:` × 106 行、`  Method:` × 186 行
（全语料 388 行 / 3190 字符）。

**为什么第三轮判错了**：R21 处理 enum 的 `Value:` 时，我把 class 大纲的种类前缀判为「载重、保留」，
理由是「class 大纲混排多种成员，读者要逐行判断」。这条理由**不成立**——大纲本来就是
**分块连续印**的（先全部 Property，再全部 Field，再全部 Method）。既然是连续块，种类就能由每块
一个表头说一次，与 enum 完全同型。而且 `locate` 的 Members 段一直就是「组表头 + 裸行」，
两处渲染同一个概念本就不该有两套写法（R4）。

**改法**：`RoslynHelper.AppendOutlineGroup`——`  Properties:` / `  Fields:` / `  Methods:` 各一行
表头，成员行缩进到 4 空格；某类为空则整块不出现（「没有这个表头」= 「没有这类成员」，比印一个
空表头少一行且同样说得清）。

**回归**：`InspectOutline_NamesEachKindOnceAsAGroupHeader` /
`OutlineModifierTests.OutlineRows_DoNotRepeatTheKindOnEveryLine`。

### R25 · 折叠行的名词槽一直空着

**症状**：`  ... +1938 more (pass limit:'all' to expand)`。

**为什么是缺陷**：全服文法（R4 定的、README 写着的）是 `... +N more <什么> (<怎么拿到>)`，
而 `locate` 五段全都把 `<什么>` 留空。Members 段最要命：它是唯一有种类子组的段，折叠行又与
**组内条目同缩进**，于是这行紧跟在 Properties 组末尾时读起来像「还有 1938 个 property」——
而它数的是 method/property/field **三类之和**。这次返回里恰好没有 `Methods:` 组，顺序读下来
会得出「locate 没找到任何名为 pawn 的方法」，而被折叠的 1938 条里就有方法。

**改法**：`ScopeArgs.FoldLine` 增设必填 `noun`，五段各传自己的名词（`C# types` / `members` /
`XML defs` / `content matches` / `files`），`trace inheritors` 传 `subclasses`。缩进不动——
locate 五段的折叠行全在 2 空格，为修一处局部歧义去破一条全局一致性，方向是反的。

**回归**：`Locate_FoldLines_NameWhatTheMoreIs`（逐条正则断言名词槽非空）。

### R26 · `inspect` def 头部的 `C# Class:` 行

**症状**：`Type: HediffDef` … 两行之后 `C# Class: \`HediffDef\``。

**为什么是缺陷**：`DefType` 就是这个 def 的 C# 类名，两行取值恒等（实现就是拿 `def.DefType`
去反查同名类型，不存在反例）。R20 把文件名收进 `SymbolRow.FileNote` 判据之后，这一行在
「文件名可推」的情形下**整行零新增事实**——全语料 8 次 def 调用，8 次都是这种情形。

**改法**：并入 `Type:` 行。三态仍各自可分：可推 → `Type: HediffDef`；不可推/多文件 →
`Type: HediffDef (Foo.cs +1 more file)`；类没进索引 → `Type: HediffDef (C# class not indexed)`。
最后一态原先靠**整行缺席**表达，读者得先知道有这条规则才读得出来——这正是本审计一路在消除的
「以缺省为信号」的读法。措辞点名 `C# class`，免得与紧下方 `File:` 行说的 def 自身文件混起来。

**回归**：`InspectDef_FoldsTheClassLineIntoTheTypeLine` / `InspectDef_SaysSoWhenTheDefTypeClassIsNotIndexed`。

### R27 · `read_code` 的错误返回丢掉了成功返回必印的文件身份

**症状**：越界消息 `Line range 1-20 exceeds file length (334 lines).` —— 一个文件标识都没有；
not-found 只给基名；三条 scope note（同名几选一 / 落到 scope 外 / 绝对路径被重定向）在四条错误
返回里**一条都不带**。

**为什么是缺陷**：`path` 收基名，多源撞名时静默取优先级最高的那一份。于是最需要说清「读的是
哪一份」的时刻——工具正在告诉你「这里没有这个东西」——身份最弱：调用方传 `path:"CompShield"`
拿到「not found in CompShield.cs」，无从判断被搜的是 vanilla 那份还是某 mod 的覆盖版，只能
改传绝对路径再来一轮，或者直接读成「这个成员不存在」。

**改法**：三条 note 先按**裸文本**攒着，成功分支再包成 `//` / `<!-- -->` 塞进代码围栏——错误返回
是纯文本，直接拼包装后的版本会在纯文本里凭空出现注释标记。越界消息补上是哪个文件，`Failure()`
改报**解析后的绝对路径**而非基名（成功分支的位置行印的就是绝对路径，两边说的必须是同一件事）。

### R28 · `sync_sources` 的未知 `action` 是七个工具里唯一挂参数表的枚举错误

**症状**：448 字符的返回里，394 字符与这个错无关——一张列着 `granularity` / `file` / `method` /
`version` / `limit` / `offset` 的参数表（这些在 `action` 定下来之前一个都用不上），外加把枚举值
说第二遍的 `('check' | 'sync' | 'diff')`，以及对「我明明传了这个参数」的调用方零信息的
`Required: no required parameters`。

**为什么是缺陷**：同类错误在别处一律是「一行 + 每个值一句括注」——`trace` 的 `Unknown mode` 88 字符、
本工具自己的 `Unknown granularity` 151 字符，都不挂参数表。**恰恰是最需要逐值括注的 `action`**
（三个动作代价从毫秒到分钟，`diff` 还有前置条件）一句括注都没有，反而用 394 字符铺参数表。

**改法**：逐值括注，并把原先只存在于 `ArgSpec.extraHint`、实际从未被印出来过的那句前置条件
（`diff` 需 `source_history_depth > 0`）吸收进 `'diff'` 那一项。随之删掉已成死代码的 `ArgSpec`
（本工具无必填参数，撤掉 `BuildUsage()` 后再无消费者）。

### F23 · `trace usages` 的两处静默削减，`search_regex` 一直在报、它一声不吭

**症状**：同一语料、同一符号 `CompShield`、同一 7 条命中——`search_regex` 末尾附
「有文件没扫全（1 个文件只扫到第 20000 行）」，`trace usages` 印 `(7 found in scope 'all')`
且零保留。

**为什么是缺陷**：两个工具有**一模一样**的两处削减——单文件行闸（`MaxLinesScannedPerFile = 20000`，
本语料里 81022 行的 `UnitySourceGeneratedAssemblyMonoScriptTypes_v1.cs` 恰好越过）与「读不开就
跳过」的裸 `catch { }`。而「没有尾注即完整命中集」是 `search_regex` 写在 Description 里的契约，
调用方顺手套到 `trace` 上，就会把一份可能漏了六万行的结果当成穷尽结论。
裸 catch 还有第二重：它连带跳过了上一行的 `matchesByFile[file] = matchesInFile`，于是该文件的
`+N more in this file` 也一并静默消失——与 F9(a) 逐字同型。

**改法**：裸 catch 改为按异常计数（`OperationCanceledException` 不吞），行闸命中也计数；两个工具
共用 `ScopeArgs.NotScannedInFullLine`。表头**同时改口**：有文件没扫全时命中总数只是下界，
`{N} found` 改为 `at least {N}`（`ScopeArgs.FoundCount`，两个工具共用）——否则一句说「7 found」、
一句说「有文件没扫全」，调用方无从判断该信哪个。

**回归**：`TraceUsages_ReportsUnreadableFiles_TheSameWaySearchRegexDoes`（同一份语料下断言两个工具
给出逐字相同的那一句，并断言表头改口）。

### F24 · `sync_sources diff` 的「history disabled」指引漏掉时序

**症状**（17 次调用里出现 8 次，是本工具的模态输出）：
`Source history is disabled. Set source_history_depth to 1 or more in config.toml to keep previous
decompiled versions for diffing.`

**为什么是缺陷**：它给的动作是「改 config」，但漏了让这个动作生效所必需的两步——`SourceHistoryStore`
在**服务构造期**一次性吃掉 `config.SourceHistoryDepth`（无热重载，须重启），而归档只在 `SyncAsync`
里写（须再跑一次 sync）。照字面执行（改 config → 重跑 diff）而不重启，拿到的是**逐字相同的这一句**、
零新信息。同一份源码里 sync 侧的同一条指引反而是完整的（`before the next sync`），于是同一个
config 项在同一个工具的两条路径上有两种详略不同的说法。

**改法**：补上「重启 + 归档由那次 sync 写」。这是本轮**唯一净增体积**处（`sync_sources` 段
+436 字符 / +15.4%）——换掉的是一次确定性失败的 `diff` 往返加一次 `sync` 往返。

## 三·四续、第五轮：R29/R30 + F25

第四轮末的判据是「逐行冗余已见底」，本轮的入口因此换成**文法自检**而非再找冗余：拿全语料
逐条比对「README 写明的共用文法」与「实际印出来的行」。三条不符，其中一条是正确性缺陷。

### R29 · 全语料出现最频的那条折叠行，两个槽都空着

**症状**：`  ... +77 more in this file`。全语料 181 条折叠行里它占 **92 条（51%）**，是唯一
名词槽与提示槽**都**留空的一形。

**为什么是缺陷**：

1. **名词非补不可**，不是排版讲究。两个工具数的都是 `regex.IsMatch(line)` 逐行累加——同一行被
   pattern 命中两次仍只算一行。不写名词时读者按「还有 77 处命中」读，而它说的是「还有 77 行」；
   一行多处的 pattern（`\bpawn\b` 之类）上这两个数能差出一截。
2. **提示槽留空会被读成漏印**。其余 19 种折叠行**全部**以 `(pass limit:'all' …)` 之类收尾，
   于是「这条没有括号」的默认解释是「服务端忘了说参数名」，而真相是**这个上限没有参数放得宽**
   （每文件预览条数是常数）。这件事推不出来，必须明说。

**改法**：名词补成 `matching lines`（`ScopeArgs.PerFileFold`，两工具共用）。「怎么才能拿到更多」
这半句**不逐文件印**，按 §R19 同一条判据上提为整份返回说一次的脚注
`... previews are capped at 3 lines per file and no parameter widens that; use read_code on a file
to see the rest`，且**只在这次真有文件被折叠时才印**（同 R9 的 `[depth N]`：没有折叠就没有这行）。
顺带把 `FoundCount` 的表头也改口成 `N matching lines` / `at least N matching lines`——表头与折叠行
数的是同一个量，此前表头只写 `N found`，那个量纲一次都没说过。

跨层的 `MaxPreviewsPerFile = 3` 由 `SourceIndexer` 的私有常量提为 public，展示层的两处字面量 `3`
改引它——两层必须同数这件事原先只写在注释里。

**代价**：这是本轮**唯一的加法**，`search_regex` +4.3% / `trace` +1.2%。买到的是「那个数到底数
什么」与「这里没有参数可传」两条推不出来的事实。

**回归**：`PerFileFold_NamesWhatItCounts_InBothScanningTools` /
`PerFilePreviewCap_IsStatedOnce_AndOnlyWhenSomethingWasFolded`（含「没折叠就整句不出现」的反向断言）。

### R30 · 名词槽的单复数：`... +1 more C# types`

**症状**：`... +1 more C# types` / `... +1 more properties` / `at least 1 matching lines`。

**为什么是缺陷**：R5 给 locate 表头定过这条规矩（「单数不写成 `1 C# types`」），而折叠行与计数
一直漏着。全语料里这一形出现在 `locate` / `inspect` / `trace` 三个工具上。

**改法**：新增 `RimSearcher.Core/Core/OutputText.cs`（放 Core 而非 `Server.Tools/ScopeArgs`，
因为 `RoslynHelper` 的大纲折叠行也要用，而 Core 引不到 Server）。裸去 `s` 在
`entries` / `content matches` / `properties` 上都会写错，故按英文构词回推：`ies→y`；
`sses/ches/shes/xes/zes` 去 `es`；其余去 `s`。覆盖的是本服务实际用到的那 11 个名词，
不做通用英文形态学。

**回归**：`FoldLine_AgreesInNumberWithItsCount`（Theory）+
`Singular_IsBuiltBackFromEachPluralActuallyInUse`（7 个实际在用的复数逐个断言）。

### F25 · `locate` 的同分并列结果在进程之间不可复现（可读性测量中带出）

**怎么发现的**：本轮与上一轮的全量转储做符号集比对，`locate` 有 **19 次调用**的符号集变了，
而本轮的改动没有一处碰排序。逐条看：`method:CompTick` 的前十条**整批换过**
（`CompEquippableAbilityReloadable` → `CompWakeUpDormant` 等五条全换），
`Vethara_Head_0` 换成了 `Vethara_Head_3`。

**为什么是缺陷**：这是 F21（`search_regex`）与 F22（`trace usages`）**同型的第三处**，且落在
三个工具里被调用得最多的那个上。候选排到 `.ThenBy(名字长度)` 就没有下一级了，同分同长的条目
之间次序落回 `matchedMembers` / def 索引的**枚举顺序**——而它跟着索引期的并发写入走。后果与
F21 一致：调用方据此得出的「这个符号不在结果里」不可复现，README 为另外两个工具明写的
「同一条查询恒给同一份答案」被顺手套到 locate 上时是假的。

`SourceIndexer.SearchTypesByName` 早已有这一级排序，注释写的正是这条判据
（「同一个查询换个进程重跑，前十条就能换一批」）——**类型搜索改过，其余四处产出候选的地方
一处没改**。

**改法**：五处产出候选的路径统一补末级定序键：

| 落点 | 补的键 |
| --- | --- |
| `SourceIndexer` 成员搜索 | 宿主类型名 → 成员名 → 文件路径 |
| `SourceIndexer` 路径/文件名搜索 | 键名，以及**同一键下多条路径之间**的路径序 |
| `SourceIndexer` 模糊成员键扩展的 `Take(10)` | 键名（这一步决定后面整批候选的**成分**，不只是次序） |
| `DefIndexer` label 搜索 | DefName → 文件路径 |
| `DefIndexer` 内容搜索 | DefName → 文件路径 |

**回归**：`Locate_TiedMembers_ComeBackInADeclaredOrder` /
`Locate_TiedDefs_ComeBackInADeclaredOrder`。这两条**不靠「重跑五次」断言**——同一进程内枚举顺序
本就稳定，那样写复现不出来、用例会恒绿；改为直接断言并列组按声明的末级键有序，那才是与插入
顺序无关的不变量。已用「把末级键翻成 `ThenByDescending` 再跑」验证过两条都真的会红。

## 五、审计中查证后**排除**的非缺陷

**5-1 · 主会话自查排除**

| 现象 | 结论 |
| --- | --- |
| 统一 diff 的上下文括号看起来错位 | 标准 LCS diff 行为，`git diff` 输出一致 |
| `version:1` 与默认值同义 | 语义自洽（「往回 1 代」） |
| fixture 结果里的 `+1 more (lower relevance)` | 无关的前缀模糊命中，非漏项 |
| fixture 的互斥条件目录只命中 1 处 | 文件级 shadowing 按 README 语义**正确**生效 |
| `inspect` 一次返回里类型名出现 3–4 次（`## C# Type: Pawn` / `Class: Verse.Pawn` / 路径尾部） | 每处承载不同事实：标题是段落标记、`Class:` 行同时给出**种类**与**全限定名**（标题只有短名）、路径给的是文件。压掉任一处都要丢事实，非纯冗余 |
| `search_regex` 冻结索引分支缺 `.Distinct()` | 一度误判为「同一文件被反复重扫」。实测证伪：`_index` 以**文件基名**为键、一个路径只落在一个键下，`SelectMany` 本就不产生重复；补 `Distinct` 是对 10k 条目的无谓哈希开销，已回退。候选文件数改前改后同为 9956 |

行为有变处已回写 `README.md`：`inspect` 的 `xmlStartLine` / 父链状态行 / `limit`（含
`'all'` 是取回被折叠成员的**唯一**途径，且不受 200 上限夹持）· `trace inheritors` 的传递闭包
语义 / 深度标注 / 零结果两分 · `search_regex` 的四类不完整尾注与 `fileFilter` 回显 ·
`limit` 非法值报错而非静默退回 · `read_code` 的目录判定、整条路径回显、同名文件几选一提示 ·
`list_directory` 的排序语义 / `offset` 分页 / 根路径回显 · `sync_sources` 的源名两分与
`source_history_depth=0` 下的 diff 指引 · 新增「参数名认不出时会说一声」一节（附「没有那行
就是全部参数都生效了」这条反向读法）。

第二轮（R1–R7 + F21）另回写：「低 Token 消耗」一节补**全服统一的截断脚注文法**（`... +N more
<什么> (<怎么拿到>)`，附三工具实例）与「返回不以空行结尾」· `locate` 的**表头分段计数**与
**「文件名只在推不出来时才印」**的反向读法（印出来的是意外，值得看一眼）· `inspect` C# 模式的
基类链改为与 def 模式同形的一行式 · `search_regex` 补「同一条查询恒给同一份答案，截断拿到的是
候选表前缀，放大 `limit` 只增不换」。

第三轮（R8–R23 + F22）另回写，一律带上**反向读法**（即「没有这行/这个标记时该怎么读」，那才是
逐行冗余删掉之后调用方真正要会的）：

- 「低 Token 消耗」补**同源标签只印一次**（行末出现来源标记 ⇒ 这段结果跨了多个源）与**扫描停下的
  那句共用脚注**（与 `... +N more` 的区别是它数不出还剩多少，故不给数字）；「文件名只在推不出来
  时才印」一句补上现在共用该判据的是 `locate` / `trace` / `inspect` 三个工具。
- `trace inheritors`：改为**只有间接后代带 `[depth N]`**，直接子类不标；全是直接子类时一个标记都
  不印，那本身就是答案。
- `trace usages`：补与 `search_regex` 同款的可复现 + 前缀单调保证。
- `search_regex`：把「展示时再按文件名排序」改成**候选表顺序就是印出来的顺序**——这是本轮才成立
  的新事实，也正是「按字母序判断某文件是真没有还是被截了」这条读法的前提。
- `read_code`：「返回里必须读到的三件事」扩为四件，新增**一行式位置注释**的文法与 `[i/N]` 编号
  （看到 `[3/3]` 就是拿全了）；`extractClass` 截断行改为报**类自己的行数**并列出两条下一步。
- `inspect`：枚举取值行不再逐行挂种类前缀；`C# Class:` 行**存在与否**本身就是索引判据
  （该行第四轮由 R26 并入 `Type:` 行，见下）。

第四轮（R24–R28 + F23/F24）另回写：

- 「低 Token 消耗」的截断脚注文法补上**名词槽恒不留空**（`... +N more <名词>`——名词说的是「这一段
  一共还剩多少」，不是紧邻上一子组的数）；`... some files were not scanned in full` 与配套的
  `at least N`（表头见到 `at least` 就说明有文件没扫全，那个总数是下界不是确定值）现由
  `search_regex` 与 `trace usages` 共用同一句。
- `trace usages`：补与 `search_regex` 同款的**完整性契约**——读不开的文件与扫到行数上限的文件都会
  在尾注里报出来，没有那行尾注即命中集完整。
- `read_code`：补**错误分支与成功分支报同一个身份**（都印解析后的绝对路径，不是基名），且三条
  scope 提示在出错时同样带出来。
- `inspect`：C# 大纲改为**按种类分块 + 每块一个表头**（`Properties:` / `Fields:` / `Methods:`），
  行内不再逐行挂种类；某类成员为空时整块不出现——**「没有这个表头」即「这个类型没有这类成员」**。
  def 模式的 `C# Class:` 行并入 `Type:` 行末尾，三态读法：带文件注 = 类在索引里；`(C# class not
  indexed)` = 不在；DefType 本身即类名故不再另起一行重复。
- `sync_sources`：`action` 非法值与 `diff` 在 `source_history_depth=0` 下的两条错误消息改为**说清
  下一步的时序**（归档由 sync 写出，故在跑过一次 sync 之前 diff 恒空）。

第五轮（R29/R30 + F25）另回写：

- 截断文法一节补**名词与 N 单复数一致**，并点名唯一不带括号的那一形（每文件折叠行）及其原因。
- 扫描类工具补**量纲**：表头与折叠行数的都是「命中行」而非「命中次数」，同一行命中两次算一行；

- 补每文件预览上限那条脚注的读法：**整份返回只出现一次、只在真有折叠时出现**，没有它就是每个

- `locate` 一节补**同分并列次序是定的**，与 `search_regex` / `trace usages` 同一条可复现保证。
