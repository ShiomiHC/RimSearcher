## 0. 这一层是什么，边界在哪

「参数层」指调用方**传进来**的那一侧，与前两轮管的「返回出去」那一侧相对：

| | 呈现层（已收） | 参数层（本文） |
| --- | --- | --- |
| 面向 | 返回文本 | 入参与它的说明 |
| 产地 | `Tools/Output/` + `Core/` | 分散在每个工具里 |
| 闸 | 73 份字节级基线 + 9 条文法规则 + 112 格矩阵 | 见 §3 |

**沿用 `单一产地重构指导` §3 的六条判据，一条不改。**其中两条在本层格外要紧：

- **判据六（闸与产品只许共用名单，不许共用判断）**——参数层最容易犯的错就是让闸去读 schema
  再拿 schema 去验 schema，那样两边同时瞎。
- **非目标里那条「工具 Description 的内容只动其中被证伪的陈述，不重写」**——本层碰的是**事实的
  产地**，不是文案的措辞。把 `200` 换成 `{HardLimit}` 属于前者；把一句话写得更顺属于后者，不做。

## 1. 动机：同一个事实现在有四份拷贝

一个参数的一件事（它叫什么、默认多少、上限多少、传超了会怎样），在本仓最多同时写在四个地方：

| # | 拷贝 | 形态 | 谁读它 |
| --- | --- | --- | --- |
| 1 | **JSON schema**（`ITool.JsonSchema`） | 手写的匿名对象，含 `type` / `default` / `maximum` / `enum` / `required` | MCP 客户端（校验与补全）、`UnknownKeyNotice` |
| 2 | **取值代码**（`ToolArgs.Get*` 的实参与其后的夹紧） | 手写的别名数组 + `fallback` + `Math.Clamp` | 真正决定行为的那一份 |
| 3 | **usage 文案**（`Description` 长文 + schema 里每个 `description` + `ToolArgSpec`） | 手写的英文散文 | 调用方（LLM）——**它照着这份做决定** |
| 4 | **README 的契约章节** | 中文散文 | 人，以及 §3 判据里那个「契约以此为准」 |

第 2 份是**事实**，另外三份是**关于那个事实的陈述**。三份陈述与一份事实之间没有任何构造性联系，
全靠写的时候恰好写对——这正是前两轮在呈现层反复治的那个形状。

规模粗测（`Sources/RimSearcher.Server` 的 `.cs` 与 README 各出现几次同一个数字）：

| 常量 | 它是什么 | Server 侧出现 | README 出现 |
| --- | --- | --- | --- |
| `200` | `ScopeAndLimitArgs.HardLimit` | 24 | 21 |
| `2000` | `ReadCodeTool.MaxLineCount` | 5 | 4 |
| `1000` | `ListDirectoryTool.MaxEntries` | 6 | 2 |
| `20000` | 单文件扫描行闸 | 3 | 3 |
| `40` | `RoslynHelper.DefaultMaxOutlineMembersPerKind` | 8 | 1 |
| `12000` | `SourceIndexer.MemberQualifiedKeyCap` | 0（在 Core） | 2 |

这些数**不都是**待还的债——同一个数字在代码里出现多次，有的是常量定义加常量引用（那是正确的），
有的才是散文里手打的字面量。逐条分类见 §2。

### 已经有的正确做法，就在同一批文件里

要紧的是：**本仓已经在做对的事，只是没做全。**至少这些散文是从常量插值出来的，改不出偏差：

- [InspectTool.cs:79](../Sources/RimSearcher.Server/Tools/InspectTool.cs)
  `$"...at most {RoslynHelper.DefaultMaxOutlineMembersPerKind} members per..."`
- [InspectTool.cs:131](../Sources/RimSearcher.Server/Tools/InspectTool.cs)
  `$"read_code extractClass truncates at {ReadCodeTool.MaxLineCount} lines..."`（**跨工具引用**，
  这一处尤其值钱：inspect 的文案里说的是 read_code 的上限）
- [ReadCodeTool.cs:113](../Sources/RimSearcher.Server/Tools/ReadCodeTool.cs)
  `$"Default is {DefaultLineCount}, values above {MaxLineCount} are clamped to it."`
- [ListDirectoryTool.cs:146](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs)
  `$"...a directory of more than {MaxEntries}..."`
- [TraceTool.cs:91](../Sources/RimSearcher.Server/Tools/TraceTool.cs)
  `$"...defaults to the server cap of {ScopeAndLimitArgs.HardLimit}..."`

故本层的目标不是引进一套新机制，是**把已有的这套做法铺满**——这与 M3 的形状相同（`CountedNoun`
也不是新发明，是把「走构词」这件已经在做的事变成唯一可能的做法）。

## 2. 现状：逐条盘出来的

盘法：七个工具逐个把 schema 一侧与取值代码一侧并排列出来，逐个属性对。下面**只列对不上的**；
对得上的那些不进表（它们是多数，尤其是「声明了却没人读」和「读了却没声明」这两个方向
**七个工具全部干净**——`ExtraAcceptedKeys` 那两道闸（`8ca8ed6`）真的守住了它要守的那件事）。

### 甲、两处**真缺陷**：别名认得，配套的「你这个参数没生效」提示认不得

这两条不是声明漂移，是**行为**上的静默——与前两轮治的那些同型，且都长在「已经修过一次的
那个坑」旁边。

**甲-1｜`read_code` 的择一提示漏了两个别名。**

- 读取侧（[ReadCodeTool.cs:324](../Sources/RimSearcher.Server/Tools/ReadCodeTool.cs)）：
  `lineCount` 取自 **5** 个名字 `lineCount, lines, count, limit, maxResults`；
- 提示侧（[ReadCodeTool.cs:235-236](../Sources/RimSearcher.Server/Tools/ReadCodeTool.cs)）：
  `linesPassed` 只探 **3** 个 `lineCount, lines, count`。

于是 `extractClass:'Pawn' + limit:50` 走进择一分支时，`Overridden(...)` 判定「没传过行数参数」，
一个字都不印。而那段代码上方的注释（220–225 行）写的正是这条缺陷本身：「三条模式互斥，择一在此前
是**静默**的……后果不是『少了点什么』而是『拿回了完全另一块代码』」。**修的时候修的是判断，
没修名单**——名单在两处各写一遍，改一处不影响另一处。

**甲-2｜`inspect` 的「limit 在 def 模式被忽略」提示漏了三个别名。**

- 读取侧（[InspectTool.cs:145](../Sources/RimSearcher.Server/Tools/InspectTool.cs)）：
  `GetDisplayLimit` 认 `LimitKeys` **5** 个 `limit, maxResults, max, count, top`；
- 提示侧（[InspectTool.cs:425](../Sources/RimSearcher.Server/Tools/InspectTool.cs)）：
  只探 **2** 个 `limit, maxResults`。

于是 `inspect name:'Human' max:5` 在 def 模式下一个字不提，`limit:5` 则会提示。同一个意图两种披露。
同样地，那段注释（421–424 行）写的也正是「返回里此前零字」这条缺陷。

**两条同一个形状**：`LimitKeys` / `lineCount` 的别名名单是一个产地，而「传没传过它」这个探测
各自又手写了一份缩短版。这正是 `8ca8ed6` 在**取值 ↔ ExtraAcceptedKeys** 之间收掉的那件事，
只是当时没往「探测」这第三处看。**收口方案是现成的：探测也去问同一份名单。**

### 乙、schema 与代码对不上的声明（不改变行为，改变调用方的预期）

| # | 工具 | schema 说 | 代码做 |
| --- | --- | --- | --- |
| 乙-1 | `trace` | `limit` 的默认是 **50**（[TraceTool.cs:101](../Sources/RimSearcher.Server/Tools/TraceTool.cs) 传 `UsagesDefaultLimit`） | `inheritors` 分支的 fallback 是 **200**（[:129](../Sources/RimSearcher.Server/Tools/TraceTool.cs) 传 `InheritorsDefaultLimit`）。一个声明后面两个默认值。**已披露，但披露在别的属性里**——写在 `mode` 的说明末尾（`The 'limit' default noted below is the 'usages' one`），读 `limit` 那一格的人看不到 |
| 乙-2 | `sync_sources` | `action` 的 `enum` 是 3 个 `check/sync/diff`（[:58](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs)） | 分支认 **9** 个（[:159-165](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs)：`sync\|update\|run`、`diff\|changes`、`check\|status\|probe`） |
| 乙-3 | `sync_sources` | `granularity` 的 `enum` 是 `files/members` | 还认单数 `file/member`（[:184-189](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs)） |
| 乙-4 | `sync_sources` | `granularity` 声明 `default: "files"` | 读取侧是 `GetOptionalString`，miss 值为 `null`；`files` 那个行为由 `wantsMembers == false` 产生。行为等价，但**声明的默认值不是任何一个读取点的 fallback**——与同文件 `action` 的 `?? "check"` 恰好相反，那一处是对上的 |
| 乙-5 | `inspect` | `limit` **连 `type` 都没有**（[:125-134](../Sources/RimSearcher.Server/Tools/InspectTool.cs)） | 全服其余 `limit` 一律 `["integer","string"]`。而这一格恰恰是**唯一**一个说明里写着「`'all'` 是取回折叠成员的唯一途径」的地方——字符串形是它的要害用法，schema 里却推不出它收字符串 |
| 乙-6 | `inspect` | `xmlStartLine` 声明 `minimum: 1`，无 `default` | 读取 fallback 是 **0**，且一切 `<= 0` 都映射成 0（[:226-228](../Sources/RimSearcher.Server/Tools/InspectTool.cs)）。有效默认值是一个被自己声明的 `minimum` 禁掉的值 |

> **乙-2 / 乙-3 这两条要小心下判断：它们八成是有意的。**
> [SyncSourcesTool.cs:180-182](../Sources/RimSearcher.Server/Tools/SyncSourcesTool.cs) 的注释写着
> 「schema 声明了 enum，但 client 不一定校验，而服务端此前只认 'members'，其余一律当 'files' 走」
> ——多认的那几个拼法是**特意加的容错**，为的是让不校验的客户端也不至于静默走错分支。
>
> 那么问题就不是「代码认多了」，而是**这条容错政策没写下来**：它现在只活在两个 `switch` 里，
> 既不在 schema、也不在散文、也没有闸。会校验的客户端仍然会把 `status` 挡在发送前，
> 而那正是容错想救的那类调用方。**这一条与丙-3 是同一件事**（见下），一并定，不要分开处理。

### 丙、系统性的三条（不是某个工具的疏忽，是同一个决定在七处的后果）

- **丙-1｜200 这个硬上限，七个工具里没有一个把它声明成 `maximum`。**
  `LimitSchemaProperty`（[ScopeAndLimitArgs.cs:147](../Sources/RimSearcher.Server/Tools/ScopeAndLimitArgs.cs)）
  只发 `type` 与 `description` 两个键，**`default` / `minimum` / `maximum` 一个都不发**。
  默认值与 200 都写在散文里——而散文那边是**插值**的（`{defaultLimit}` / `{HardLimit}`），
  所以人和 LLM 读到的数不会错，**错的是机器读到的**：校验型客户端对 `limit` 一无所知。

  更麻烦的是**同一个参数名两种声明法**：`list_directory` 与 `sync_sources` 的 `limit` 是各自
  手写的，它们**有** `default` / `maximum`；走 `LimitSchemaProperty` 的那三个没有。
  「同一个东西两处各写一遍」的经典后果——两处长得不一样，而没人看得见这件事。

- **丙-2｜256 字的模糊查询上限，三处强制、零处声明。**
  `ToolArgs.MaxFuzzyQueryLength`（[ToolArgs.cs:66](../Sources/RimSearcher.Server/Tools/ToolArgs.cs)）
  卡着 `locate.query` / `inspect.name` / `trace.symbol`，三个 schema 都只写了 `minLength: 1`，
  没有一个写 `maxLength`。**唯一的硬约束恰恰是没声明的那个。**

- **丙-3｜所有 `integer` 属性实际都收字符串与浮点。**
  `GetInt`（[ToolArgs.cs:111](../Sources/RimSearcher.Server/Tools/ToolArgs.cs)）与 `GetDisplayLimit`
  都比声明宽。这一条**不一定要改**：宽进严出对 LLM 调用方是好事（它经常把数字写成字符串），
  而 `sync_sources` 的 `sources` / `version` 声明成 `["string","array"]` / `["string","integer"]`
  正是**特意**为此写宽的——同一个仓里既有「特意声明宽」的先例，也有「悄悄收宽」的现状。

  故本层真正要定的是一条政策：**「服务端比 schema 收得宽」是有意的还是疏忽的？**
  连同乙-2 / 乙-3 / 丙-2 一起，答案只能有一个，且要写下来。定成「有意」就把它补进 schema
  与散文（让校验型客户端也享受到），定成「疏忽」就收紧代码。**现在这两种情况在七个工具里并存，
  而版本之间的区别只是当时谁写的。**

### 丁、`ToolArgSpec` 是第三份手写的参数名单

[ToolArgs.cs:240](../Sources/RimSearcher.Server/Tools/ToolArgs.cs) 的 `ToolArgSpec` 收两个手打字符串：
`requiredSummary` 与 `allParameters`，用来在缺参时印一份用法。六个工具各写一份
（`sync_sources` 没有——它没有必填参数，一致）。

`allParameters` 是 schema `properties` 那份名单的散文版。**实测当前六份全部对得上**
（逐个比对 schema 属性名与散文里列的名字，无一遗漏无一多余）——但没有任何一处保证它继续对得上，
而它坏起来是**静默的**：加一个 schema 属性、忘了加进散文，缺参提示就少列一个参数，一条测试都不红。

`requiredSummary` 里的别名列表已经开始漂了：`locate` 那份写「Aliases accepted: name, symbol,
pattern, search」，而读取点还收 `term`；`trace` 那份写「query, name, type」，读取点还收
`symbolName` 与 `typeName`。**都是漏列而不是错列**，故不会把调用方引到错的方向，但它证明了
这份名单确实在漂。

### 戊、散文里手打的数字（本层最典型的一笔）

同一份文件里，同一个数**一处插值、一处手打**——这是最能说明问题的形状：

`trace` 的 [Description:52](../Sources/RimSearcher.Server/Tools/TraceTool.cs) 手打
`"up to the server cap of 200"`，而**同一个文件** [:91](../Sources/RimSearcher.Server/Tools/TraceTool.cs)
的 `mode` 说明写的是 `$"...the server cap of {ScopeAndLimitArgs.HardLimit}..."`。两句说同一个 200，
一句改得动一句改不动。

逐条（**已核对为当前正确**，故这是债不是缺陷——债的定义就是「现在对，且没有任何东西保证它继续对」）：

| 散文 | 手打的数 | 它的常量 |
| --- | --- | --- |
| `TraceTool.cs:52` `up to the server cap of 200` | 200 | `ScopeAndLimitArgs.HardLimit`（`InheritorsDefaultLimit` 就等于它） |
| `TraceTool.cs:54` `(default 50, at most 3 preview lines` | 50 / 3 | `TraceTool.UsagesDefaultLimit` / `TraceTool.MaxMatchesPerFile` |
| `SearchRegexTool.cs:45` `at most 3 preview lines per file and at most 50 files` | 3 / 50 | `SourceIndexer.MaxPreviewsPerFile` / `SearchRegexTool.MaxFilesShown` |
| `ListDirectoryTool.cs:134` `(default 100, server cap 1000)` | 100 / 1000 | 无常量 / `MaxEntries` |
| `ListDirectoryTool.cs:162` `limit (default 100)` | 100 | 无常量 |

最后两行还牵出一件小事：**`list_directory` 的默认值 100 根本没有常量**——它是
[:171](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs) 里 `GetInt(args, 100, …)` 的一个裸字面量，
而同类的 `SearchRegexTool.DefaultMatchLimit` / `ReadCodeTool.DefaultLineCount` /
`SyncSourcesTool.DefaultLimit` 都是具名常量。**四份拷贝里没有一份是产地**——这一处得先造一个产地，
才谈得上让另外三份去引用它。

## 3. 现有的闸：一条很强，其余靠人盯

### 已经对的那一条，写法就是本层要照抄的样板

[`UnknownParameterNoticeTests.EveryKeyAToolReads_IsDeclaredAsAccepted`](../Sources/RimSearcher.Tests/UnknownParameterNoticeTests.cs)
（`:97`）是本仓参数层唯一一条**两侧都不手抄**的判据：

- **名单**从产品源码里刮出来（正则扫该工具 `.cs` 里所有 `ToolArgs.Get*` / `TryGetElement` 的字符串
  实参），`scope` / `limit` 两族则直接取 `ScopeAndLimitArgs.ScopeKeys` / `LimitKeys`；
- **判断**交给产品自己的 `ToolArgs.UnknownKeyNotice`——注释就写着「闸这边不重写一份『什么算认得』，
  否则两边一起错时照绿」。

这正是 §3 判据六。它的反方向 `EveryKeyAToolDeclares_IsActuallyRead`（`:132`）同样成立。
**本层要做的事，就是把这两条的做法铺到别的属性上。**

它有两处已知的钝角，动它之前要知道：

1. 刮取用的正则只吃一层括号嵌套，读取点如果搬进 `ScopeAndLimitArgs` 之外的第三个辅助类，
   就整片扫不到——**扫不到的表现是键集变小，即判据变松，绿**；
2. 工具 → 源文件的映射按 `tool.GetType().Name + ".cs"` 猜，一个工具的取参代码若分在两个文件里，
   同样是静默少扫。

### 覆盖面上最大的一个洞：**三份手写的工具名单，没有一份来自注册表**

| 名单 | 位置 | 形态 |
| --- | --- | --- |
| 真正注册的 | [Program.cs:150](../Sources/RimSearcher.Server/Program.cs) | `new ITool[] { … }` 七个，带真实构造实参 |
| 参数层闸用的 | [UnknownParameterNoticeTests.cs:188](../Sources/RimSearcher.Tests/UnknownParameterNoticeTests.cs) | 另一个手写 `ITool[]`，**构造重载都不一样**（如 `new ListDirectoryTool()` 对 `new ListDirectoryTool(scopeCatalog, conditionalFolders)`） |
| 输出层矩阵用的 | [OutputGrammarGateTests.cs:60](../Sources/RimSearcher.Tests/OutputGrammarGateTests.cs) | 七个**字符串**名字 + 七个字段 |

**没有任何一处断言这三份一致。**后果：新加一个工具，参数层与输出层的闸全部保持绿——它压根不在
名单里。这与 M3 治好的那件事同型（「名词的产地是调用点的实参」），也与输出层矩阵那个已知弱点同型，
故它不是本层独有的债，而是本层**最先撞上**的那一笔。

### 完全没有闸的属性（按急迫度排）

| # | 没人守的性质 | 坏起来是 | 现成的反例 |
| --- | --- | --- | --- |
| 洞-1 | **schema 声明了的属性，真的有读取点吗** | **绿** | `EveryKeyAToolDeclares_IsActuallyRead` 的注释明写把 schema 属性排除在外（「那是工具的正式参数，认得它们是定义而不是额外声明」）。于是把 `fileFilter` 的读取点改个名而 schema 不动，这个参数会被 `UnknownKeyNotice` 认作合法（它正是从 schema 反射来的）**然后静默吞掉** |
| 洞-2 | **schema `default` == 代码 fallback** | **绿** | `list_directory` 的 `100` 独立写了**四遍**：散文 [:134](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs)、`@default` [:136](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs)、`ArgSpec` [:162](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs)、读取 fallback [:171](../Sources/RimSearcher.Server/Tools/ListDirectoryTool.cs)。测试里还有第五遍 |
| 洞-3 | **schema `maximum` == 代码夹紧** | **绿** | 同上，`1000` 写了三遍。现有的三条夹紧测试验的都是「服务端确实夹了」，**没有一条验「夹到了 schema 广告的那个数」** |
| 洞-4 | **散文里的数 == 常量** | **绿** | 见 §2 戊 |
| 洞-5 | **`ToolArgSpec.allParameters` == schema 属性** | **绿** | 见 §2 丁 |
| 洞-6 | **schema `required` == `GetRequired*` 调用点** | **绿** | 无 |
| 洞-7 | **`MaxFuzzyQueryLength` 真的用在每个模糊槽上** | **绿** | 只在一个假 spec 上测过；`locate` / `inspect` / `trace` 哪个退回 `GetRequiredString` 都看不出来 |
| 洞-8 | `ITool` 的 `ReadOnlyHint` / `BypassIndexGate` / `SuppressStalenessNotice` / `Title` | **绿** | 全仓零测试。`sync_sources` 是唯一一个非只读工具，这件事没人断言 |

**八个洞，八个「绿」。**这不是巧合：参数层的东西全都不进返回文本，故 73 份字节级基线一个字都照不到。
这就是判据乙（P0 必须最先做）的全部理由。

### 输出层那套办法搬得过来吗——搬得过来，且接缝已经在了

输出层是**两个文件的分工**：`GrammarRules.cs` 是一套只吃文本、与工具无关的规则；
`OutputGrammarGateTests.cs` 是 7 × 16 的矩阵加三条遍历器（跑规则 / 防 fixture 退化 / 查覆盖完整）。
本层对应过来：

- 一份 **`ParamRules`**：吃一个工具的 `(JsonSchema, ExtraAcceptedKeys, ArgSpec, Description, 读取键集)`
  五元组，回答洞-1 到洞-7。手法甲（同一产地喂两组实参求公共框架）在这里**直接可用**：
  `LimitSchemaProperty(50, …)` 与 `LimitSchemaProperty(100, …)` 的公共部分就是它的框架，
  差异处就是那个默认值——不必在闸里手抄 `50` / `200` / `1000`。
- 一张 **工具 × 属性种类的矩阵**，N/A 格必须写理由（照抄 `TheMatrixCoversEveryToolAndBranch`），
  **但它的工具名单必须从注册表推导**，否则就是把上面那个洞原样复制第四遍。
- 一份 **`ParamRulesTests` 式的反面用例**：每条判据配一条故意违规的输入。理由与
  `GrammarRulesTests` 开头那段逐字相同——本层每一个洞的失效签名都是「继续绿」。

## 4. 约束与判据（本层特有的三条）

`单一产地重构指导` §3 那六条全部继承。本层另加三条，都是从前三轮的教训里长出来的：

### 甲、**schema 不许拿 schema 验**

`UnknownKeyNotice` 已经是从 `tool.JsonSchema` 反射出属性名的（[ToolArgs.cs:230](../Sources/RimSearcher.Server/Tools/ToolArgs.cs)
的 `SchemaPropertyNames`），这是对的——它让「schema 说认得什么」与「提示语说认得什么」按构造一致。
但**闸不能沿用这条路**：拿 schema 去断言 schema 自己，两边同时错时一片绿。

闸要问的是 schema 与**另一侧**（取值代码、夹紧、常量）对不对得上，故：
**schema 一侧允许反射读取（那是名单），另一侧必须独立取得（那是被比对的事实）。**同 §3 判据六。

### 乙、**改文案的那一步，判据是「基线出现 diff 且 diff 只在文案里」**

`Description` 与 schema 的 `description` **不进** 73 份输出基线（它们走 `tools/list`，不走
`tools/call`）。故这一层没有现成的字节级闸——**这是本层与前两层最大的不同，也是最大的风险**：
改文案改错了，929 条测试一条都不会红。

对策不是「小心点」，是**先立闸**（同 §3 判据三）：动文案之前先给 `tools/list` 的完整响应立一份
字节级基线。这份基线不判对错，只回答「这次改动动了哪些字」，与呈现层那 73 份同一个作用。
**这一步必须排在所有文案改动之前，且单独一个 `test:` commit。**

### 丙、**「四份拷贝」不是要削成一份**

README 那一份（拷贝 4）不能由代码生成，也不该：它是**给人读的契约**，判据里点名以它为准。
schema 那一份（拷贝 1）也不能删，它是 MCP 协议要求的。

真正的目标是让**同一个事实只有一处可修改**：常量是那一处，其余三份要么插值引用它，要么由闸盯着。
**「一份拷贝」与「一个产地」不是同一回事**——`CountedNoun` 那一轮就是这么落的：名词在产品与
README 里照样各出现很多次，但**改动点**只有注册表一处。

## 6. 还没想清楚的（不装作想清楚了）

1. **`ParamRules` 的「产地」到底是什么。**输出层那套之所以成立，是因为每一句输出都有一个函数把它
   渲染出来，闸可以喂两组实参求公共框架。参数层的 schema **不是渲染出来的**，是一个手写的匿名对象
   ——`LimitSchemaProperty` 那种走公用工厂的部分能用手法甲，而 `list_directory` / `sync_sources`
   自己手写的那些**没有产地可问**。可能的出路有两条（都没验证过）：把手写的那几处也收进工厂，
   或者承认这一层的闸只能做「两侧对比」而做不到「问产地」。**这个问题不解决，P3/P4 就只是把
   字面量从产品挪进闸。**

2. **`Description` 该不该有闸，闸什么。**现有的五条断言全是手抄子串（`OutputReadabilityTests` 那三条
   + `ListDirectoryPagingTests` + `CrossReferenceTests`），且只覆盖 3 个工具；`trace` / `search_regex` /
   `read_code` / `sync_sources` 的 Description **一条测试都没有**。但「散文该说什么」本身不可判定，
   能判定的只有里面的**硬事实**。故 P5 之后大概率就到头了——再往上是文案评审，不是闸。

3. **P0 那份基线的粒度。**七个工具各一份、还是整个 `tools/list` 响应一份？后者更简单，但一个工具
   改一个字会让所有人的 diff 都变。倾向前者，未验证。

4. **本文要不要真的做。**§1 那张表把参数层记作 🟡 而不是 ✗，是因为它**至今没出过事故**——
   `单一产地重构指导` §4 末尾对 schema 那笔债的原话是「它是理论债，十三轮盲测没在这儿出过事故」。
   §2 甲那两条改变了这个判断的一半（那是真缺陷，只是没被盲测撞上），另一半没变。
   **P0 + P1 + P2 的收益是清楚的；P3 往后要不要做，建议等 P1 修完再评估。**
